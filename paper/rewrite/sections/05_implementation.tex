\section{Implementation}
\label{sec:impl}

Section~\ref{sec:design} says when each packet should leave, but a forwarding pipeline has no way
to wait: a P4 program runs to completion per packet and can read a clock, yet it cannot sleep or
schedule a callback.

\subsection{Holding a packet with queues}
\label{sec:impl:queues}

\begin{figure}[t]
\centering
\IfFileExists{figures/fig_design.pdf}{\includegraphics{figures/fig_design}}{\figplaceholder{One P4 pipeline: ingress classifies every arrival and arms deadlines; a read lane holds the acknowledgment and the response; a control lane holds the OPERATE; each held packet sits behind a queue of generated blocker packets that a strict-priority scheduler drains first.}}
\caption{How one pipeline realizes the schedule. Ingress classifies each transaction and computes
  its release deadlines. Blocker packets drained ahead of the held packet sustain a hold until its
  deadline expires, and the on-chip packet generator keeps those blocker queues non-empty. The
  four-queue ladder holds what the outstation returns; the second pair holds the outgoing OPERATE,
  not a second reply. Solid lines are master-facing and observed; dashed
  lines are not, as in Figure~\ref{fig:observation}.}
\label{fig:design}
\end{figure}

The switch does carry a traffic manager with several queues per port and a strict-priority
scheduler, the primitive with which SP-PIFO approximates programmable scheduling on today's
hardware~\cite{alcozSPPIFOApproximatingPushIn2020}. Since a scheduler decides what does \emph{not} leave, we hold a packet by using that property
rather than a timer.

A READ uses \emph{four} queues on one internal port, as Figure~\ref{fig:design} shows. Two carry
the packets we delay, the acknowledgment and the response, and above each of those sits a
\emph{blocker queue} in strict priority carrying small packets the switch generates itself. While
blockers keep arriving, the packet beneath them is never served, and each hold ends when its own
blocker queue runs dry. The response does not queue behind the acknowledgment, having its own held queue and its own
blocker gate, which lets the switch schedule the two releases independently. In descending
priority the ladder runs acknowledgment blockers, held acknowledgment, response blockers, held
response.  Blockers circulate on an internal loopback port and never reach a cable, so neither endpoint
can observe them. Each carries a tag naming its transaction and lane, so a leftover blocker
cannot delay a later transaction.

No count drives this timer. Instead the program stores an absolute release instant
when the acknowledgment arrives, quantized to a 256~ns grid, and each of the 64 recirculating
blockers compares the current timestamp against it: while the difference stays negative the
program regenerates the blocker, and once it turns, the program drops it. Since the deadline decides when the
packet leaves, the blockers only have to keep the queue non-empty until then, so the reservoir
becomes sized for continuity rather than for duration.

The queue does not empty at the deadline, however. Since each blocker tests the deadline on its
own pass, those still queued when it passes are served once more before the queue runs dry,
allowing the held packet to leave. The release therefore trails the deadline by the time that draining takes, and
each lane drains its own queue, the acknowledgment's above the response's;
Section~\ref{sec:eval:limits} reports what we measured of that interval. The arrangement makes the
coupling of Section~\ref{sec:design:model} implementable: the program computes the response's
release instant at the acknowledgment, so the hold absorbs whatever the outstation does without the switch measuring it.

\subsection{One READ transaction}
\label{sec:impl:walkthrough}

The request arrives, a table classifies it by function code, and the program forwards it at once.
It records a transaction in flight and the acknowledgment to expect. When the
acknowledgment arrives at $t_A$, a median of 0.56~ms after the request on our relay, the
program writes both release instants from that one timestamp, which places them on the
same instant $t_A$ that Section~\ref{sec:design:model} requires. It does so once from an unarmed sentinel so a duplicate acknowledgment cannot arm a
second deadline. The acknowledgment enters the hold queue and the packet generator fills the
blocker queue. A response that arrives before its deadline queues behind the acknowledgment,
and the two leave in order at their scheduled instants. A response that arrives after its deadline has no remaining wait to serve. The program marks it
late and commits it to the same response-hold queue rather than to a bypass, as in
Figure~\ref{fig:timeline}(b). It leaves when that queue next serves it, so its departure is
prompt but not instantaneous. Releasing the response clears the transaction state.

The two lanes hold different packets. The four-queue ladder above
holds what the outstation sends back, the acknowledgment and the response, for READ and for both
phases of a control alike. The second loopback port carries a pair of queues for the opposite
direction: blockers above a held \emph{OPERATE request}, on its way to the relay. So the control
extension adds a hold the read path does not have, while the same machinery releases the packets the
master observes in both cases. Giving the OPERATE its own scheduling domain keeps the
higher-priority read reservoirs from starving it.

The queues stay separate; the transaction state does not. All lanes share the deadline registers. Every register that
records a transaction holds a single slot, and the control path writes the same release instants
at OPERATE admission that the read path uses, so the program protects one transaction at a time
rather than one per flow.

The evaluated configuration satisfies that assumption by construction: the driver serialises its
exchanges and every capture carries one connection. Where a second transaction would arm while one
runs live, the program does not interleave them silently; it classifies the arming attempt as busy
and forwards the packet unprotected rather than taking the deadline already in progress. The
claim covers the deadline, not the rest of the transaction's state. The program writes the
expected relay sequence and acknowledgment earlier in the same pass than it reaches the busy
verdict, so we claim it for the serialized workload we evaluated and not in general. Per-flow
protection would need per-flow state and a way to index it, which this program lacks and
we did not evaluate.

\subsection{Failing open}
\label{sec:impl:failopen}

Almost every path through the program ends in a forwarding decision. A packet outside the protected
session, an unrecognized request, an acknowledgment with no armed transaction and a response whose
transaction has retired all leave unchanged, so such an exchange loses its protection and
still arrives. One path behaves differently. The
control lane keeps a released OPERATE's application generation as a spent marker until the next
SELECT clears it, and the switch drops a later OPERATE carrying that generation. A retransmission the
master sends to repair an OPERATE lost after the switch forwarded it carries exactly that
generation. Consequently the switch discards the packet that would have repaired the loss
(Section~\ref{sec:eval:limits}). A budget on blocker passes bounds every hold: once a reservoir has spent
its budget, the packet leaves and its state clears. The budget counts passes rather than
elapsed time, so the horizon $H$ of Section~\ref{sec:design:params}, 30.8~ms here, records what
the control plane computes from the budget and an assumed service rate rather than a
wall-clock deadline the data plane keeps. With the timing mode off the same program forwards
everything immediately, which is how we collected the Timing OFF arm.

\subsection{Resources and testbed}
\label{sec:impl:p4}

The program runs to about 1{,}560 lines of
P4$_{16}$~\cite{bosshartP4ProgrammingProtocolIndependent2014} for the Tofino Native
Architecture, compiled
with the Barefoot SDE 9.13. It occupies all twelve ingress match-action stages of one pipeline and six egress stages, with
112 tables. State is small: one-entry registers reached by stateful ALU actions, one access per packet per
register, the most the architecture permits. One 25~Gb/s port carries the master and one 1~Gb/s port the relay. Two further ports serve as
loopbacks carrying no cable: the first carries the four-queue read ladder, the second the control
extension's pair, blockers above a held OPERATE. The second loopback sits in its own scheduling
domain, so the higher-priority read reservoirs cannot starve the OPERATE reservoir. Six queues across two
loopbacks in all.

Every policy quantity lives in a runtime table entry, so an operator changes policy by writing entries
rather than loading a program. The loaded build realizes the dual-deadline schedule only, because its
arming table admits that mode alone. The acknowledgment-only and response-only limits of the model
therefore describe the design rather than settings of this build: configuring them left both
packets unheld, with the measured interval the outstation's own.

The control plane, about 890 lines of Python, brings up ports and queues, installs the
packet-generator configuration, and writes the timing parameters and reads them back. It refuses through a clamp, not through the admission arithmetic. It rejects a request for an acknowledgment
hold above 40~ms outright before any write, which we confirmed on the switch, and the
acknowledgment offset $A$ on the control lane must exceed the largest admissible $J$ plus a bound
on the outstation's acknowledgment latency. It computes and reports the horizon $H$ of
Section~\ref{sec:design:params} without enforcing it, which is exactly why the
sweep of Section~\ref{sec:eval:policy} can install settings beyond it and find where the
mechanism leaves its operating region. The outstation, an SEL-751A feeder
protection relay, belongs to one of the DNP3 device classes whose timing Formby et al.\
fingerprint~\cite{formbyWhosControlYour2016}. The master issues READ and select-before-operate
operations to isolated control points through a guarded driver, so no control operation in the
evaluation moves a breaker.
