\section{Background and Motivation}
\label{sec:bg}

In this section, we first present the DNP3 transactions the framework protects. Then we explain why
the timing of these transactions identifies a device and how a programmable switch can change that
timing.

\subsection{DNP3 Read and Control Transactions}
\label{sec:bg:dnp3}

\begin{figure}[t]
\centering
\IfFileExists{figures/fig_ladder.pdf}{\includegraphics{figures/fig_ladder}}{\figplaceholder{DNP3 transaction ladder: (a) READ request, TCP ACK, application response; (b) SELECT, TCP ACK, SELECT response, OPERATE, TCP ACK, OPERATE response.}}
\caption{The two DNP3 transactions on the master-facing link. (a) A READ poll and its CLRT. (b) A
  select-before-operate control and its master-visible interval $O$.}
\label{fig:ladder}
\end{figure}

DNP3 carries supervisory control and data acquisition traffic over TCP between a master and an
outstation~\cite{ieeeIEEEStandardElectric2012}. In Figure~\ref{fig:ladder}, we show the two
transactions the framework protects. The master polls the outstation with a READ request, function
code 1, and the outstation returns the requested measurements in a response, function code 0x81. A
control command instead uses select-before-operate. The master sends a SELECT, function code 3, that
names an output point, and the outstation confirms it. The master then sends an OPERATE, function
code 4, which the outstation executes and confirms with a solicited response.

Because DNP3 runs over TCP, the transport layer of the outstation acknowledges each request. The
acknowledgment travels in a segment of its own before the application answers, although TCP also
allows it to ride on the response~\cite{eddyTransmissionControlProtocol2022}.
Each exchange appears on the wire as three packets: a request, a transport acknowledgment
carrying no DNP3 payload, and a DNP3 response. We limit the framework to the three function codes
above, READ, SELECT and OPERATE, and it forwards every other exchange unchanged.

\textbf{Definition 1. Cross-Layer Response Time (CLRT):} the interval between the arrival of the
transport acknowledgment and the arrival of the DNP3 response of the same exchange, measured on the
link to the master.

\textbf{Definition 2. Physical Operation Time:} for a select-before-operate command, the interval
between the OPERATE command and the moment the commanded physical change occurs at the device.
Formby et al.\ estimate it in two ways, from the arrival of the unsolicited event response at a tap
and from the sequence-of-events timestamp the response carries in its
payload~\cite{formbyWhosControlYour2016}. They report that the arrival-time estimate produced no
usable results and retain the payload timestamp as the physical fingerprint.

\subsection{Execution Time as a Fingerprint}
\label{sec:bg:fingerprint}

An outstation answers a request twice, from two different layers. Its TCP stack acknowledges the
request as soon as it arrives, whereas its application responds only after the device has done the
requested work. Because both packets travel the same path in the same direction, the common propagation delay
cancels. Consequently, the CLRT is dominated by the execution time of the outstation.

Execution time differs between device models, since vendors implement the same function with
different hardware and algorithms, and it differs between the operations one device performs. Formby
et al.\ classify DNP3 device types and models by the distribution of the
CLRT~\cite{formbyWhosControlYour2016}, and Lin et al.\ measured the execution times of three
devices, among them the SEL-751A we evaluate, and separated them by the combination of their average
and their variation~\cite{linDefRecEstablishingPhysical2020}. The same separation holds between the operations
of one device. For example, the median CLRT of our relay is 2.929~ms for a control command and 2.121~ms for
a poll, while its median acknowledgment latencies for READ, SELECT and OPERATE lie within
0.003~ms of one another. Consequently, the CLRT carries how this device performs
an operation, which is the profile a fingerprinting adversary builds.

\subsection{Holding Packets in a Programmable Switch}
\label{sec:bg:switch}

A programmable switch exposes a match-action pipeline, written in
P4~\cite{bosshartP4ProgrammingProtocolIndependent2014}, that parses headers, keeps state in
registers and places packets into output queues at line rate. Each egress port offers several queues
served in strict priority, a primitive that can also approximate programmable
scheduling~\cite{alcozSPPIFOApproximatingPushIn2020}. Because such a pipeline can delay a packet and
release it later without a host in the loop, a switch between the master and the outstation can hold
the acknowledgment and the response of a transaction and release them on a schedule the operator
sets. As such, the switch can change the timing an adversary observes without changing either
endpoint or any byte of the payload.
