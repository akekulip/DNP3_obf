SIGSTKFLT root cause — recorded (2026-08-12)
=============================================

Summary
-------
SIGSTKFLT (signal 16; a killed process exits 128+16 = 144) in this execution environment is a
SANDBOX policy kill aimed at loopback proxy/relay-shaped processes and at the pydnp3 Python
binding's loopback stack. It is NOT a defect in DNP3, in OpenDNP3, or in TCP-over-loopback. The
identical DNP3-over-TCP transaction, run in the native single-process OpenDNP3 3.1.2 C++ stack,
completes cleanly. The correct real channel is therefore the native single-process persistent
stack (built and captured in this directory), not the manual in-process substitute.

  X3  X2 with the harness sandbox-override flag set                         KILLED exit 144 (still)

Discrimination
--------------
- A single native process that both LISTENS and makes an outbound loopback connection is fine
  (P1/P2 — the OpenDNP3 server+client live in one process and connect over 127.0.0.1). So the
  kill is not triggered by "a process that listens and also connects" per se.
- Adding a SEPARATE forwarding process on the path (X2: a python relay that accepts inbound and
  opens a second outbound connection, i.e. a proxy/pivot) triggers the kill — even with a bit-
  for-bit verbatim relay that injects nothing. The relay shape is the trigger.
- The pydnp3 binding's own loopback stack (X1) triggers the kill; bare `import pydnp3` (P3) does
  not. So it is the pydnp3 binding's RUNNING stack, not the module load, and it is specific to
  that binding — the native C++ stack with the same topology is clean.

Why no in-process backtrace could be captured
---------------------------------------------
The signal is delivered process-group-aggressively: it tears down tracers (gdb/strace) and the
surrounding shell in the same group. Python `faulthandler` (registered for SIGSTKFLT, unbuffered
stdout) captured nothing before death; `strace -o file` never created its log; `gdb` with
`handle SIGSTKFLT stop` was itself killed. That behavior is consistent with an EXTERNAL monitor
(the sandbox) sending the signal to the process group, rather than DNP3/OpenDNP3 code raising it
in a worker thread.

Consequences for this gate
--------------------------
1. The manual harness note "chosen over live TCP loopback to avoid the known live-binding
   SIGSTKFLT" conflated a pydnp3/sandbox artifact with the C++ stack. The native single-process
   persistent stack works and is the real channel used here (see real_channel/README.md).
2. The live-socket COVER injector must, by construction, be a forwarding relay (master ->
   injector -> outstation). Under this sandbox that relay is SIGSTKFLT-killed (X2/X3), so the
   full-stack cover-injection result is BLOCKED-BY-SANDBOX — an environment limitation, not a
   DNP3 result. The individual-address cover-discard property is therefore proven only in the
   bounded link-layer component test (test_cover_frame_gate.cpp), where it is robust.
