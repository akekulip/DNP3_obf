## Restart-path coverage

The m10 change is the stage-1 RST restart, counted in `count_busy[5]`. For each block, the after-snapshot minus
the before-snapshot of cell 5 is reported:
- **nonzero:** the restart path ran on silicon. The block's verdict then also covers it.
- **zero:** the restart path was **not exercised** on silicon. The block shows only that m10 behaves as m9 on the
  paths it did take. It is never reported as a pass of the restart path.

## Reset-interleaving block (Step 4b): defined before it runs

Block 6, `ctl_m10_interleave_950_01`: tool `candidate_interleave` (`rearm_01/hw/candidate_interleave.py`), config
`ctl_m10_interleave_950.json`, arguments `--arms combined --fixtures separate_ack`. It runs last, after blocks 1–5,
through the same frozen runner.

**Tuple.** The probe tuple is 192.0.2.61 → 192.0.2.62:20000, master port 59970: TEST-NET-1 addresses that no Vision
interface owns. The injector refuses otherwise, and changes no route, firewall rule, namespace, NIC setting or
sysctl. Its link addresses are those of the probe's own frames, so the installed rows match them.

**Schedule** (`interleave_probe.build_interleave_plan`; 10 points, 140 frames, one raw socket). For each kind (READ,
SELECT) and each offset in {0, 1, 2, 3, 5} µs:
1. handshake, request and the outstation's bare ACK;
2. after 5 ms, the master RST, then the outstation response `offset` µs later;
3. a 300 ms settle;
4. a same-tuple reconnect with new ISNs: READ request, bare ACK, response;
5. a closing RST.

**Why 5 ms before the RST (an inference, not a measurement).** The model's restart case lets the ACK settle for
120 ms because each model lap takes milliseconds. On silicon a recirculation lap is about 1 µs. The bare ACK goes to T
(`commit_before_t`) and back to N through `N_ACK_RETURN`. If N's work cell stays owned only for those passes, it is
idle within microseconds. If it stays owned until T commits the ACK, the relevant hold is about the 2 ms ACK delay
plus shaping, and 5 ms is then about 2.5 times that, not a wide margin. Neither duration has been measured. The
outcome is safe either way: if the cell is busy at the RST's stage 0, the RST takes the busy-retry path
(count_busy[2]) and the block reports NOT_EXERCISED, never PASS. The model's 24/24 used a different driver and frames:
it supports the mechanism, not this schedule.

**Verdict** (`interleave_probe.judge_interleave`), from the out and in captures and the counter snapshots:

| verdict | condition |
|---|---|
| FAIL | at any point: the first request or the first RST was not relayed to the outstation exactly once; the first response reached the master more than once, after the reconnect began, or not as the 61-octet image; any other master-bound payload in the point's window; the reconnect READ not delivered exactly once with the 61-octet image. Run-wide: a busy drop, retry exhaustion, stale retry, duplicate abort or T fallback |
| NOT_EXERCISED | no failure, but count_busy[5] did not rise. Never reported as a pass |
| PASS | no failure, and at least one restart |
| INVALID | the injector failed or sent fewer frames than planned; tcpdump statistics are missing or show a drop; a capture is empty or short; a counter cell is missing or decreasing. Never blamed on the switch |

**Limits.**
- Offsets are measured at the host transmit hook, never assumed. Host timing makes a window hit a matter of chance.
- The revised reset contract (no release after T applies the reset) cannot be observed on silicon. At most one copy
  is enforced, and the count is reported.

## Residual risk: two compilers

The model suite runs the `compile_local` image (SDK 9.13.1). The switch loads `compile_switch_9132` (SDK 9.13.2).
m10_02's compiled defect (a new metadata field, `../m10_bisect_01`) was found on the 9.13.1 model and its mechanism
was not established. Whether 9.13.2 behaves the same is not shown by any model run. The recovery blocks on silicon
are the only test of the 9.13.2 image.
