The RST therefore never closed N's lifecycle, and N kept the tuple. That explains why every later same-tuple
handshake drew no frames.

Because the RST bytes are identical in both runs, `client_diff` or `server_diff` (RST seq − N's `client`, native
ack − N's `server`) was non-zero in 02 only. N's stored client or server sequence differed between the runs at
that moment. The log does not print those register values, so which one differed, and which earlier pass wrote it,
is **not determined**. Attempt 02 retried the duplicate response once against four times in 01, and that is the
first observed difference.

This matches the open, pre-existing N behaviour recorded for m4/m5 (`DESIGN.md` m5): N refuses a master RST that
does not match its stored sequence state, and same-tuple reconnect then fails until the tuple is closed. Here it
is reached through the duplicate-response interleaving. The m8 E change is not on this path, since N decided before
E or T saw the RST. Smallest next step: read `p0.n_Ingress.client`/`server` at the RST (an instrumented replay of
