## Findings that should be corrected before a final PASS

### 1. Isolation v2 can spend the same old blocker twice

Location: `H/token_window.py`, `full_run_rejections_v2`, lines 438–451.

`seeded_max` counts old tokens not rejected raw. The function allows that many stale-blocker retirements before the permit, then allows the **same full population again** after the permit, plus fresh tokens.

Independent counterexample: eight old READ tokens, seven raw READ rejections, four old OPERATE tokens all rejected raw, no fresh tokens. There can be at most one seeded blocker. Set one stale retirement before the permit and one after. The function accepts both. The supplied reproduction script demonstrates this without editing the repository.

Use a joint conservation inequality, or subtract pre-permit retirements from the remaining old population:

`post_stale <= fresh_tokens + old_seeded_max - pre_stale`

Also require nonnegative populations and consistent counters. This remains an upper bound: normal retirement/timeout may have removed other blockers. It does not identify individual blockers or prove every old blocker drained before the permit.

The retained D1 data have zero pre-permit stale blockers, so this correction alone does not change that run's arithmetic. Fix the checker without inventing a new dataplane defect.

### 2. A drain interval overlapping a deadline is being promoted to success

Locations: `H/token_window.py::drain_timing_v2`, lines 465–492; `S/analysis/isolation_v2.py`, lines 65–75.

The function labels a drain `consistent` when its **lower** bound is below the deadline. The recomputation then treats `consistent` as `cleanup_ok=True`.

Actual retained D1 result:

- interval: 14.954303790–15.112161832 seconds;
- deadline: 15.001 seconds;
- recomputed `cleanup_v2.ok=True`, overall `ok=True`.

That observation is compatible with meeting the deadline and with missing it. It supports an indeterminate result, not a deadline guarantee. Use three states: pass when the upper bound is within the deadline; fail when the lower bound exceeds it; otherwise indeterminate. Preserve the interval and measurement resolution.

There is also a bracketing problem: `diag_poll.py` reads cells sequentially within each sample's `t_start_ns`/`t_end_ns`. The current formula uses previous-sample end times as though the relevant counter were read exactly at the end. Either timestamp the specific reads, or conservatively bracket each event using the full read windows. Validate monotonic timestamps/counters, read errors and completion of the expected cohort before calling the last observed increment the drain.

Do not rerun a full campaign for this. First recompute existing evidence. Only a specific unresolved deadline claim needs a targeted higher-resolution observation.

### 3. Model PASS does not require driver provenance

Location: `CT/model_summary.py`, lines 25–66.

The new summary correctly retains every attempt and blocks a later failure. However, it merely displays `driver_sha256`; the PASS predicate checks source hash, totals and exit code, not driver identity. I removed every launch record's driver hash in a temporary copy; the summary still returned `model_gate_passed`.

The abort driver illustrates why this matters. Both attempts have the same wrapper hash `a0276bbf…`, but the actual imported contention driver changed:

- abort attempt 01 inner hash: `ca0b965d…`;
- abort attempt 02 inner hash: `55a3030a…`.

The result metadata retains those inner hashes; the summary does not expose/validate them. Record and verify the executed wrapper plus imported driver/dependency closure, source/build identity and selected sections. Require a coverage manifest so a restricted section cannot masquerade as the complete driver. Retained failures need a specific resolution reference, not simply an unvalidated `RESOLVED:` prefix.

The CLI currently exits zero even for `blocked`. That is acceptable for a reporting command only if callers inspect its verdict. Add an explicit enforcing mode with nonzero exit for a failed gate; do not silently change reporting semantics.

### 4. The live isolation path still uses v1

`H/candidate_isolation.py` imports and calls `full_run_rejections`, not `full_run_rejections_v2`. `isolation_v2.py` is a retrospective recomputation and intentionally copies the other v1 judgments.

Therefore, do not describe the running m9 isolation block as using v2 qualification unless an outer, recorded step actually evaluates it. After correcting v2, select its acceptance version explicitly, bind that version to the run, and ensure the final verdict consumes it. Keep v1 results immutable.

The recomputation removes failures using substrings such as `rejection`, `cleanup bound` and `OUT_TOKEN_STALE`. Replace that with explicit component identifiers; unknown failures and missing component verdicts must remain blocking. This is a small acceptance interface change, not a new experiment family.

## m9 correctness: credit and remaining limits

The N reset-wait correction is a real, bounded change. Its source tests reproduce the m8 failure when a same-tuple SYN claims the work cell between the reset's passes. m9 waits and delivers one reset; the tests cover longer busy periods, duplicate resets and budget exhaustion. The design note explains the observed 12/24-byte normalization difference as a downstream consequence of the previous connection failing to close. I verified the regression and new source, but did not independently replay the large retained compiler-model trace establishing that causal history.

Keep the limitations in `CT/evidence/m9_01/NOTES_20261016.md` visible:

- The reset waits only while owner and epoch remain unchanged; an owner-changing event still aborts it.
- A SYN encountering the waiting reset may be dropped and require ordinary TCP retransmission.
- Exhausting the 32-wait budget still aborts the reset; worst-case N traversal cost can increase.
- The parser accepts reserved values 0–63 although the intended writer generates at most 32; the internal-origin assumption should be an asserted interface invariant.

Do not claim the owner-changing case requires a noncompliant sender: network reordering or prior packets in flight can also change observed ordering. Record it as a scoped limitation unless the supported workload excludes it with evidence. This review is not directing an unbounded reconnect redesign.

The independent abort driver is useful, but its negative checks at offsets 48/50 currently assert only no forwarded reset and no E-16 increment. Require the promised surviving response/connection behavior from the already-captured record too. `held_before_rst` is inferred from absence of release/fallback, not positive proof of response admission. Bare RST remains a disclosed untranslated limitation. Do not call all reset forms qualified.

## Efficiency work that is ready now

The attached package rebases the three earlier probes onto the exact m9 source. No working-tree or hardware configuration was changed.

| Probe | Change | Potential benefit | Unproved risk |
|---|---|---|---|
| `n_zero_unused_timestamp` | Write zero to five unused N handoff timestamps; preserve header length/validity | Reduce PHV pressure and timestamp dependencies | Compiler may already eliminate some cost; no predicted stage saving |
| `t_single_child` | Remove child-1/2 state and accesses; explicitly reject nonzero child IDs | Fewer stateful resources, metadata and dependencies | CP initialization/snapshots must use the candidate schema; stage reduction not demonstrated |
| `n_bank_diffs` | Compute differences from old sequence-bank values in the register actions; select operands earlier | Shorten read→subtract→classify dependency | SALU constraints or added operand metadata may prevent placement or erase the benefit |

The three SBO transport segments are created later in E. They are **one T response event**, so removing unused T child lanes does not remove SBO segmentation.

For each probe I compared endpoint bytes/times, counters and state across READ/SELECT/OPERATE at four ACK/response spacings. I also ran 14 m9 reset regression cases per probe, including preservation of the documented owner-changing limitation. No SDK compilation was performed here. The older 130-case lifecycle runs were on m8-based probes; they must not be represented as m9 results.

Compile each probe independently, starting with the timestamp and single-child changes. Retain both success and failure reports. Measure table placement, stage span, PHV, SALUs, SRAM/TCAM/hash resources and parser/deparser effects. Only then combine demonstrated wins. A shorter source file or fewer tables is not evidence of fewer hardware stages. Do not trade integrity checks, stale-generation guards or timing precision for a smaller stage count.

Keep E's current mapping/CRC path stable during this pass. Historical CRC factoring is a later capacity experiment, not a proven E-stage reduction. Record total internal packets and bytes separately from stage count and original-packet laps.
