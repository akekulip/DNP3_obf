01 / WHAT IS BEING STUDIED

Not a bare ACK — the response that rides on it

The outstation piggybacks its DNP3 response onto the very TCP segment that acknowledges the master's request — measured on 9 of 9 requests. So the ACK time and the response time are the same wire observable. The subject is response-time normalization of the ACK-bearing DNP3 response, not "delay the ACK."

Five things get conflated under the word "ACK." Only two exist on this wire, and only they can be shaped:

In plain terms — the device answers so fast that its reply and its "got it" are the same packet. We can nudge when that packet leaves; we never touch what's inside it.
02 / THE MEASURED LEAK

The device's configuration is written in its response time

We didn't assume the leak — we measured it, running the existing analyzer over real rig captures. The outstation's processing time rises in an almost perfectly straight line with the number of control points (CROBs) it is asked about. Toggle the view to watch the signature disappear under normalization.

Response processing time vs. request complexity

What the attacker does

A passive on-path observer that reads unencrypted DNP3 fits a line to the response times it sees and reads off the number of control points — a proxy for the device's configuration. (The separate database-size channel on the read plane is a planned measurement, not yet shown.) The fitted line is clean enough that a handful of polls pin it down.

What normalization does

Release every response on a class-independent schedule — a common target distribution that doesn't depend on how long the device actually took. The slope collapses to ≈0, the fitted line goes flat, and the number of control points is no longer recoverable from timing.

Honest caveats. The fit is one sample per N-level — a clean 10-point line, not yet a replicated law (replication with confidence intervals is the first planned experiment). It is one software outstation, one rig — an information-theoretic / regression result, not a device-identification claim (that needs ≥2 stacks). And the measured variable is CROB count — control-command complexity, a different mechanism from outstation database size, whose leak lives on the Class-0 read plane and is still unmeasured. No defense has been run yet; "watch it disappear" shows the design target, to be demonstrated by the planned defended runs.
03 / NORMALIZATION vs. RANDOMIZATION

Why not just add random jitter?

Because a patient observer averages jitter away. In SCADA the master polls on a fixed schedule, so the attacker gets the same measurement over and over.

Randomization — averageable

Add i.i.d. jitter and the released time is T_class + noise. Over n polls the sample mean converges to the true class mean with error shrinking as 1/√n. The secret is recovered; jitter only raises the sample count.

Normalization — not averageable

Reshape the released distribution to be class-independent. Averaging now converges to the same target for every class, so nothing about the device is recovered. This is the goal I(time ; complexity) → 0.

The clean line from the advisor's own work

This is also the structural difference from RAINCOAT (Lin, Kalbarczyk & Iyer, IEEE Trans. Smart Grid, 2019 — the advisor's own paper). The two are complementary, not competing:

AxisRAINCOATThis work
MechanismRandomize → misdirectNormalize → make indistinguishable
Leaked thingGrid state / contentDevice configuration (control-point count / complexity; identity is a future ≥2-stack claim)
LocusCooperating endpointsIn-network, byte-preserving pass-through
In plain terms — jitter is a disguise you can see through if you stare long enough. Normalization gives every device the same face.
04 / OPERATIONAL SAFETY

The real limit is TCP, not DNP3 — and safety beats privacy

Every DNP3 timer in this stack is 5–60 seconds (re-verified in the OpenDNP3 source). The binding constraint is two orders of magnitude tighter: the master's effective TCP retransmit timeout. Overshoot it and the master retransmits — the single loudest tell to both a passive observer and a Zeek correctness IDS.

LimitValueRole
Effective TCP RTO (master)≈200 ms floor*BINDING — overshoot ⇒ retransmit ⇒ visible
Master app response timeout5 sbackstop
Outstation solicited-confirm5 sbackstop
Outstation SELECT→OPERATE10 swhole SBO wall-clock
Link keep-alive60 sidle only

*The 200 ms floor is a Linux default (TCP_RTO_MIN), not universal — the effective value must be measured on the master before any budget is fixed. A fixed 15–20 ms normalization deadline kills the ms-scale leak with ~10× RTO margin and 100×+ DNP3-timer margin.

Which traffic to shape, and which to leave alone

DNP3 fields reveal the type of an operation, never its physical criticality. So the element ships default-conservative: shape the read plane fully, gate controls through an operator allowlist, and never delay a control it cannot prove is non-critical.

Traffic classVerdictWhy
Integrity / Class-0 READshape fullyMain periodic leak surface; no control semantics
Event READshape — tight boundCarries alarms/SOE; don't defer operator awareness
SELECT responseshape to fixed deadlineCarries the CROB-count leak; gate by criticality allowlist
OPERATE responseshape / bypass if criticalControl completion; command latency + safety dominate
Application CONFIRMbypassMaster-originated; holding risks flow-control stall
Unsolicited responsebypassAlarm-driven, latency-sensitive (off by default here)
In plain terms — you have seconds of slack from DNP3 but only a couple hundred milliseconds before TCP complains. Stay well under that, shape the routine reads, and never make a real control command wait.
05 / THE SYSTEM

Where the delay lives — and the first build

Because the replay/split server generates its response bytes, it schedules the send directly. There is no live packet to intercept — which rules out kernel/eBPF/DPDK machinery for the first deliverable and puts a clean scheduler at the application layer.

Outstation / replay
Hulk · generates response

Byte-preserving bump-in-the-wire: the normalizer only chooses the release instant of packets that already exist; b"".join(chunks) == original still holds.

Recommended first implementation

  • Application-layer absolute-deadline release inside the existing server
  • monotonic_ns + one sleep — sub-ms precision, no thread-per-packet, no busy-wait
  • Configurable target distributions: constant · uniform · bucketed · size-decorrelation · decoy-match
  • Strict budget with immediate-release fallback; full telemetry (requested/actual delay, deadline miss, reason); reproducible seeds; CSV/JSON export

Cited to reject

Timing wheels, calendar queues, DPDK, AF_XDP and tc/netem exist to delay live packets at millions/sec. DNP3 runs at single-digit kbps with under one held frame at a time — so one timer is correct, and the heavy machinery would be over-engineering. They become relevant only if the defense later moves to a true in-path proxy.

06 / PROGRAMMABLE HARDWARE

What each platform can actually do

The six mechanisms split cleanly. Pacing and gap-normalization are native everywhere but bound rate, not latency. The decisive move — first-packet absolute delay — is native on a DPU/FPGA but not on Tofino.

*On Tofino, absolute delay is reachable only via a recirculation + timestamp-deadline loop — unbuilt and unmeasured on our chip, and affordable only because DNP3 is low-rate/small-frame. Presented as de-risked future work, never as a result. BlueField (Accurate Send Scheduling) and FPGA are the honest native homes. Closest published precedents: ditto and NetWarden (both Tofino).

The reviewer's attacks, answered

A hostile IEEE/ACM reviewer will press on these. Expand each for the honest answer.

H1Does response time really correlate with database size?›
partly — don't over-state

For CROB count: yes, decisively and measured (R²>0.99). For database size specifically: not yet — that's a separate planned experiment. The briefing keeps the distinction everywhere and claims only the CROB-count correlation.

H3Do fixed/bounded delays create a NEW fingerprint?›
real risk — tested, not assumed

Two vectors. First, an always-exactly-15.00 ms response is itself unusual — mitigate with a class-independent distribution (uniform-within-budget or decoy-match) over a degenerate constant. Second, and sharper: a single normalizer in front of one outstation makes shaped vs. unshaped traffic trivially separable — the protected device becomes a beacon, more identifiable, not less. The anonymity-set benefit needs a fleet shaped to a common distribution. Both are added as experiments (residual conditional info across P3/P4/P7, plus a detectability-of-the-normalizer test).

H4Can the attacker average away the randomization?›
yes for jitter, no for normalization

i.i.d. jitter is averageable; class-independent normalization is not. The claim is attacker-model-dependent (a repeated-poll passive observer — the SCADA case) and is stated that way. A dedicated averaging attacker makes it measurable: finite samples-to-halve for jitter, unbounded for normalization.

H5Is one software outstation enough?›
no — scoped by a claim ladder

One device supports the information-theoretic / regression claim. A device-classification claim needs ≥2 stacks (a second implementation and/or a real relay/RTAC) — flagged as the single highest-value missing asset.

H6Is the P4/Tofino implementation realistic?›
mixed — honestly framed

Native pacing/gap normalization: real. First-packet absolute delay on Tofino: only via an unbuilt recirculation+deadline loop — future work with a de-risking argument, never a demonstrated result. BlueField and FPGA are the native homes.

H7Is shaping control-side traffic operationally acceptable?›
yes, if gated — safety dominates privacy

The leak sits on SELECT/OPERATE responses, so killing it means shaping control-side timing — safe on the response-timing axis (huge margins), but gated by an operator criticality allowlist because DNP3 fields can't certify a control is non-critical. Default: bypass controls unless whitelisted.

08 / EVALUATION

How success gets proven

An attacker ladder from a trivial threshold to a defense-aware model, run against a grid of timing policies, measured with information-theoretic and classifier metrics — reporting the conditional leak I(time ; complexity | size), because the size channel stays open in the byte-preserving phase.

Attacker ladder · A1 → A8
  • A1 threshold · A2 template · A3 random forest
  • A4 gradient boosting · A5 SVM · A6 1D-CNN (if justified)
  • A7 defense-aware — trained on obfuscated traffic
  • A8 repeated-observation — averages many polls (the jitter-killer)
Policies · P0 → P8
  • P0 native · P1 fixed delay · P2 additive jitter
  • P3 constant-time · P4 bounded randomized normalization
  • P5 bucketed · P6 size-decorrelation · P7 decoy-match · P8 gap-normalization
  • Pre-registered test: does P6 dominate P2 at equal privacy, lower latency?

Metrics & the honest bar

  • Privacy: classifier accuracy / AUC drop; regression β & R² before/after; mutual information (KSG + bootstrap CI); Wasserstein-1 / KS distance to the target distribution.
  • Cost: added latency (mean/p95/max), poll-completion time, the privacy-vs-latency Pareto with a shaded safe-operating region (added latency < RTO margin ∧ correctness = 100%).
  • Correctness bar (same as splitting): identical measurements, DNP3 CONFIRM, 0 retransmits / 0 resets, byte-preservation asserted.
