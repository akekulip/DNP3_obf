01 / THE PROBLEM

One secret, two channels

Ask an outstation to operate N control points and its reply gets both bigger and slower, almost perfectly in step with N. A passive watcher who never decodes a byte can read N back off either channel. Toggle "normalize timing" below — and watch the size line stay put.

Concrete exampleA SELECT for 5 control blocks → a 95-byte reply that takes ~1.9 ms. A SELECT for 16 → a 256-byte reply taking ~3.9 ms. The size grows 14.6 bytes per control block; the attacker just measures the reply and divides.

How the reply encodes the control-point count

Why it matters — normalizing the timing is real progress, but it only closes one of the two doors. The size door stays open, and (as we'll see) nothing byte-preserving can shut it today.
02 / THE THREE TOOLS

Split, pad, timing — what each actually does

They are not interchangeable. Each touches a different property of the traffic, and each has a very different reach against the two leaks above.

Split · reshape structure

Cut one reply into many packets

Re-divides a response into smaller wire units at safe boundaries, preserving every byte and its order. Changes packet count and segmentation — but not total bytes.

can't hide size
Pad · add apparent size

Make a small reply look bigger

Add bytes / packets / volume so a small transaction resembles a larger target. The only tool that could close the size leak — but no safe byte-preserving form exists in DNP3.

future phase only
Timing · control when

Release replies on a shared clock

Hold each reply until a class-independent deadline, so timing no longer depends on the secret — and unlike random jitter, a patient attacker can't average it away.

buildable now
03 / SPLIT

Splitting reshapes — but never hides total size

On the rig, a 2407-byte read reply was cut into as many as 141 tiny paced packets, and the master reassembled every byte with zero retransmissions. Useful on big reads. But drag the slider and watch the one number that never changes.

1 (finest)
chunks on the wire 141 total packets 301 total bytes 2407 (never changes)

When splitting helps

Large multi-frame read replies: cutting a big response into many small paced packets defeats classifiers that key on per-packet size or the natural frame pattern. Cut on DNP3 checksum-block boundaries so a watching IDS still sees clean sub-units.

When splitting backfires

On small control replies (few chunks, no size benefit); at a fixed pattern (self-fingerprint); without pacing (the OS re-merges it); and at the finest setting the chunk count itself scales with size — so it relocates the leak to packet count instead of removing it.

Correction worth knowingThe receiver reassembles a split cut at any byte offset — TCP plus a stream-reading parser put it back together regardless. Cutting on checksum blocks is our auditability choice, not a requirement. What the receiver rejects is a changed byte (bad checksum). And a split only stays split on the wire if it's paced; a zero-delay "aggressive" split can be re-merged by the sending stack.
04 / PAD — THE NEGATIVE RESULT

There is nowhere legal to hide filler in DNP3

Padding is the only tool that could close the size leak. But every in-band way to add filler is blocked. We tried the obvious one (fake control points) and the outstation rejected it on the wire. Tap each category to see why it fails.

The honest bottom line. No byte-preserving, semantically-inert DNP3 padding exists at any layer: invalid filler is rejected, valid filler becomes real data or a real command, and the protocol has no length field and no "ignore-me" object. The only clean way to hide size is to wrap DNP3 in an encrypted tunnel and pad the tunnel — future work, needing both ends to cooperate, at roughly +590% bandwidth to fully hide a control reply.
The example that proves itPad a SELECT with fake control blocks at nonexistent indexes? The outstation answers OUT_OF_RANGE for each fake index — visible on the wire — and a partial failure blocks the real OPERATE. The padding isn't just useless; it breaks the transaction.
05 / TIMING

Why normalization beats random jitter

The intuitive fix — add random delay — fails against a SCADA attacker, because the master polls on a schedule and the attacker sees the same reply many times. Press play: the jitter estimate homes in on the truth; the normalized one never does.

An attacker averaging many repeated polls

Two hidden classes (N=2 and N=8). Poll repeatedly and watch whether the attacker's running average can tell them apart.
The rule — jitter is averageable (its noise cancels over many samples, revealing the true per-class mean); a class-independent schedule is not (every class converges to the same target, revealing nothing). The catch: this holds against a repeated-poll observer — state the attacker model, and report the leak conditioned on size, since size still carries the secret.
06 / THE HEADLINE

Timing is closeable now. Size is a residual.

Put the three tools against the two leaks and an asymmetry falls out — the study's core finding, and its most defensible contribution.

07 / THE DECISION POLICY

So — when do we do what?

Pick a transaction and see the recommended decision. The dominant strategy: shape the read plane hard, bypass the control plane by default.

Why control is bypassed by default — control traffic is at once the lowest-privacy-value class (it's rare, so the attacker gets few samples) and the highest- safety-cost class to delay. The read plane is the opposite: high-value (polled constantly) and near-zero risk. So shaping reads and bypassing controls wins on both privacy and safety at once.
08 / SAFETY & THE TIME BUDGET

The real limit is TCP, and safety beats privacy

Every DNP3 timer is 5–60 seconds; the binding limit is two orders tighter — the master's TCP retransmit timeout. Overshoot it and the master retransmits, the one thing both a passive watcher and an IDS can see. But it's three separate limits, not one running total.

Limit 1

Initial hold < RTO

How long you delay the first reply must stay under the measured retransmit timeout.

Limit 2

Each gap < RTO

Every inter-chunk gap must be under the RTO — each paced chunk is acknowledged as it arrives.

Limit 3

Total < 5 s

The whole transaction must finish inside the DNP3 app/select timeout — 25–70× looser.

Why bpc=1 is safe despite 1.4 seconds of pacing141 chunks at 10 ms each spans 1.41 s total — yet it ran with zero retransmissions, because no single packet ever waited more than one 10 ms gap for its acknowledgement. The per-hop gap binds, not the running total. (Measure the actual timeout first — ~200 ms is a Linux default, not a law — and note a split is governed by the outstation side, a timing hold by the master side.)

DNP3 fields reveal an operation's type, never its physical criticality — so the element ships with an operator allowlist and bypasses every control unless explicitly cleared. Protection tripping doesn't travel over DNP3 at all. Fail open: any doubt, release untouched.

10 / WHAT WE HAVEN'T PROVEN YET

The honest limits (a hostile reviewer's list)

This is a design + preliminary-measurement study. No defense has been run yet. Expand each.

Both leak lines are one sample per point›
The R²=0.9999 size line and R²≈0.99 timing line each have a single measurement per control-point count — a clean 10-point line, not a replicated law. The first owed experiment is ≥30 repetitions per point with confidence intervals.
The payload is unencrypted — why does metadata matter?›
A full deep-inspection observer reads the control count straight off the cleartext, so this defense targets a no-inspection / NetFlow-grade observer now, and reaches full value only under a future encrypted tunnel. But the in-network mechanism (parsing the function code, cutting on visible checksum blocks) only works on cleartext — under a tunnel, shaping must move to the endpoints. That mechanism discontinuity is stated, not hidden. The top experiment (A0) measures exactly how much a direct payload read already recovers.
Size ≠ database size›
The measured 14.6 B/CROB is control-command complexity, a different mechanism from outstation database size (which leaks on the read plane, ~5.7 B/point). Don't conflate them.
One device; no defense executed›
One software outstation supports a configuration-complexity result, not device identification (that needs ≥2 stacks). And no defense has been run — every "closes it" is a design target until one defended rig run exists. The effective retransmit timeout is also still to be measured on both hosts.
