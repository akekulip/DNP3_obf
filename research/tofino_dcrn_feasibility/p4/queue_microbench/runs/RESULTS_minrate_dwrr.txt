=== DWRR (byte-fair round-robin, sched_cfg dwrr_weight, NO rate cap) ===
  SPARSE (input ~50 pps, one REAL queue):
     DEQ = 50 = input, depth 0 -> clean passthrough; round-robin manufactures NO cadence.  [mb_dwrr_sparse.txt]
  BACKLOG both REAL queues (dports S1=20001 S2=20002, ~154k pps in, equal weight 1):
     S1 DEQ ~77,000 pps steady (median 77174), queue depth 0 (drains as fast as it fills);
     the other ~77k pps is S2 -> DWRR splits the two backlogged queues ~50/50 by weight and
     drains at ~line rate. NO absolute pacing.                            [mb_dwrr_backlog2.txt]
  PROCEDURE NOTE (corrected mid-run): the FIRST dwrr backlog attempt read S1 DEQ=661 because the
  setup's per-queue entry_mod left the prior min-rate R=600 cap (max/min_rate_enable=True,
  min/max_rate=600) in place -> the dwrr arm was silently capped. Confirmed by reading sched_cfg
  live. Fixed the setup so --mech dwrr explicitly writes min_rate_enable=False + max_rate_enable=False;
  re-armed (verified caps cleared) and re-ran -> the clean ~77k pps above. The dwrr SPARSE result is
  unaffected (50 pps < 600 cap, cap never binds).
  -> Pure DWRR imposes NO absolute cadence: it only arbitrates the RATIO between queues that are
     CONTINUOUSLY NON-EMPTY. To pace a sparse flow it needs a PORT-level cap + chaff to keep the
     queues backlogged (the heavy-chaff Ditto route — separately untested, high overhead).

=== VERDICT (completes the locked-mechanism scheduler sweep) ===
Neither MIN-RATE/GUARANTEED-RATE nor DWRR can pace a sparse low-rate flow DIRECTLY (without heavy
chaff). Both reproduce the max-rate-shaper conclusion: a TM scheduler paces BACKLOG, not a sparse
flow. For a ~5 Hz DNP3 obfuscation cadence the only mechanisms that clock a sparse flow remain:
 (1) the pktgen / recirc METRONOME (proven: manufactures a steady ~100 pps ±1 from zero input), or
 (2) Ditto-style CHAFF-FILL keeping the queues continuously backlogged >=~600 pps (high overhead).
The "round-robin scheduling" idea (that DWRR/min-rate could pace a low-rate flow cheaply without a
metronome or chaff) is REFUTED on silicon: TM scheduling is fundamentally a backlog discipline.

Caveats: switch-side counters (not host pcaps); Vision OFF (dp9 hairpin); backlog input ~150k pps
(stronger than the prior run's ~8100, but the cadence conclusion is rate-independent for input>>R);
only min=max-pinned min-rate tested (a min-rate floor BELOW an uncapped max was not separately swept,
but the sparse passthrough already shows the floor does not pull a sub-R flow up).
