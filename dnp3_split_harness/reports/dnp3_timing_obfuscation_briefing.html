01

The threat: a device is legible by its rhythm

Formby et al. (NDSS'16) showed that an outstation's cross-layer response time — the gap between its TCP ACK and its DNP3 application response — is stable enough to identify the make and model of the device behind an IP. It is a side channel that survives even when every payload byte is encrypted or unremarkable.

We parsed six real captures (three device models, ~23,000 transactions) to see the fingerprint directly. Two regimes appear, and they are cleanly separable:

02

The defense: hold, don't jitter

The naïve idea — add random delay — is wrong, because native + jitter leaves the device's own processing time inside the observable. The correct design measures a target from request arrival and releases at the later of "ready" and "target":

target_delay   = sample from a common, class-independent distribution
desired_release = request_arrival + target_delay
actual_release  = max(response_ready, desired_release)   # never send early

The target must not depend on response size, CROB count, device identity, or native ready time — so two different responses become indistinguishable in time. It runs inside the existing byte-preserving replay/split server, as a hold placed immediately before the bytes go on the wire. Nothing about the DNP3 frame changes: join(chunks) == response still holds, no CRC is recomputed, no ACK is forged.

Three modes

  • native — wire-identical passthrough; only adds a timing log.
  • fixed — every response released at one configured target.
  • bounded — target sampled from a seeded uniform band.

Fail-open, always

Five bypass conditions send immediately and log the reason: target already missed, queue over depth, unsafe target above the measured RTO floor, critical traffic, or unknown flows. The defense can degrade a device's anonymity, never its availability.

Why it's safe to holdThe measured TCP retransmission floor on this stack is ≈ 211 ms (not the folklore 200). Every target tested (10–25 ms) sits far below it, so a held response never trips a retransmit. That's the headroom the next section spends.
03

How we ran it on real hardware

Loopback is a smoke test; the bar is two physical servers over a real link. Here is exactly what happened, including the parts that fought back.

  1. Deploy. The rig hosts only had the pre-split harness — no timing module — so the current code + replay payloads went to both over rsync, and I confirmed it parsed before running anything.
  2. Rep model. The replay server serves one captured integrity poll then exits, so each repetition restarts the server and runs one poll from the master (~5 response transactions), appending one row per response to the server's timing log. Seven configurations × 30 polls = 930 timed transactions.
  3. Wire witness. With sudo on the rig, tcpdump on the outstation NIC captured native / fixed-25 / bounded runs — the authoritative attacker-visible timing and the TCP-health check.
  4. Verify, don't assert. Every claim below is read back from the server's per-transaction log or the pcap, not from a script's exit code.
Challenges met along the way Three real ones: (1) no sudo at first — the core matrix was designed to need none (unprivileged port, app-level correctness), and the wire capture waited for the credential; (2) the probe's own capture returned empty under sudo-over-SSH, so I captured externally with tcpdump instead of trusting the tool; (3) SSH throttling under the rapid restart loop threw transient 255s — paced calls fixed it. None changed a result; all are logged.

05

Result B — inducing a separate ACK, without forging

The SEL-751's fingerprint lives in the gap between a separate pure ACK and the response. Can a host produce that split on demand just by delaying its write — no synthesized packets? We swept the write delay from 0 to 50 ms and watched the outstation's own egress.

Why this result matters twice It bounds Phase 1: the 10–25 ms normalization targets all sit below 40 ms, so they keep the flow in the combined regime — normalization pins the response time without accidentally minting a separate-ACK signature. And it opens Phase 2: to manipulate the ACK→response gap directly, a host can simply hold ≥ 40 ms and the separate ACK appears for free — no P4 recirculation, at the cost of a ≥ 40 ms visible floor.
06

Is the fingerprint obfuscated? Channel by channel.

The honest answer is "the timing channel, yes; the whole device, not yet." We trained a device-model classifier on the real traces and simulated the defense on its features, using a capture-level split so adjacent packets can't leak across train and test.

Timing channel

◆ Obfuscated · rig

The one place response latency uniquely identifies a device (AB1400 vs ION7550) collapses to the 0.5 chance floor under a constant target — their timing vectors become identical. Rig-proven pinning does this.

Response-size channel

▲ Survives today

ION7550's 37/61-byte responses stay distinct from the 37/54 devices. A byte-preserving timing hold never touches size — size_only accuracy is identical before and after (0.500).

held · sign-off

+ Size padding — complementary, not yet approved

◈ Mechanism built · rig-tested

A separate primitive, validated one step ahead of sign-off: built on the OpenDNP3 outstation (real-but-inert points) and run on the rig — a small device padded up to a large one gives a byte-identical 361 B response, 0 resets. The device-ID drop to 0.797 (size_only → chance 0.400) stays a trace-feature simulation. Held pending go-ahead; not part of the committed defense.

ACK-mode channel

▲ Survives

The SEL-751's early pure ACK (~4 ms) isn't held by a response delay, so ackmode_only is also invariant (0.800). Closing it needs the Phase-2 ACK-timing primitive (section 05 shows it's reachable).

The one-line verdict Bounded response-time normalization closes the timing channel — rig-proven, safe, byte-preserving — but device identity here rides mostly on response size and ACK mode, which a timing hold cannot touch. Framed correctly, this is a timing-channel defense, not a full device-anonymizer. The size leak wants padding; the ACK leak wants the Phase-2 primitive we've now shown is reachable.
07

Under the hood — the code, made simple

The whole defense is one small decision, taken once per response, right before the bytes go on the wire. Here is that decision in the real code, with the jargon stripped out.

In one sentence

Instead of sending each reply the instant it's ready, we pick a target time — the same kind of target for every reply — and send at that target. Fast replies wait; nothing is sent early. Two replies that took different amounts of work now leave at the same moment, so an outsider can't tell them apart by timing.

1 · The one decision that matters

# three timestamps, in nanoseconds, from a monotonic clock
native_ready    = response_ready  - request_received   # how long the device actually took
desired_release = request_received + target_delay      # when the POLICY wants to send
actual_release  = max(response_ready, desired_release)  # never send before it's ready
hold            = actual_release - response_ready       # the extra wait we added
Plain version: measure the target from when the request arrived, not from when the reply was ready. Send at max(ready, target) — so if the reply is already done we still wait for the target, and if the target has already passed we send immediately. The device's own "thinking time" (native_ready) disappears into a fixed release time.

2 · Why not just add random delay?

The tempting version is send_time = ready + random_jitter. It fails, because the device's real thinking time is still sitting inside ready — you've just smeared it, not hidden it. Average enough samples and the fingerprint reappears. Measuring from request arrival and flooring to a common target is what actually removes the signal:

✗ wrong   visible = native_thinking_time + random_jitter   # thinking time still leaks
✓ right   visible = max(native_thinking_time, target)      # two replies → same target
The test we run on every reply: join(chunks) == original_response. The hold changes when bytes leave, never which bytes — no CRC is recomputed, no field edited, no ACK forged.

3 · Where it plugs in

The hold is a single hook inside the existing replay/split server, placed immediately before the write. Everything else — matching the request, reconstructing the exact response bytes, waiting for the master's confirm — is untouched.

request_received_ns = now()                # stamp arrival, before any work
chunks   = build_response(request)         # exact captured bytes (unchanged)
decision = scheduler.decide(...)          # the block-1 math → a release time
wait_until(decision.actual_release_ns)     # the hold (absolute deadline, not sleep-loops)
send(chunks)                              # bytes leave at the target
native mode sets the target to zero, so the hook is a pure pass-through — the wire looks byte-for-byte and timing-for-timing identical, it just also writes a log line. That's what makes "before vs after" an honest comparison on the same code path.

4 · It fails open, always

Five conditions make the server skip the hold and send immediately, each logged with its reason. The defense can cost a device some anonymity — never its availability:

  • Target already missed — the reply took longer than the target; send now.
  • Unsafe target — a hold longer than the measured RTO floor (105 ms) would risk a retransmit; send now.
  • Queue too deep — back-pressure past the limit; send now.
  • Critical traffic — control-bearing requests are never held.
  • Unknown flow — anything the server can't safely reason about.

Across all 930 rig transactions, zero of these fired — every target sat comfortably under the safety floor.

5 · The size padding built · rig-run

The size leak survives because ION7550's replies are 61 bytes where others are 54. We close it without forging bytes: give the OpenDNP3 outstation extra input points that are real but inert, so its own Class-0 response grows to a common size. This is now implemented and measured on the rig (Fig 13).

# run_outstation.py — real flags, added this session
# pad-* add inert Class0 input points ON TOP of the function points.
python3 run_outstation.py --num-analog 20 --num-binary 20 \
        --pad-analog 20 --pad-binary 20     # 40+40 real+pad = 80 points

# under the hood — exact per-type database, no stray slots:
db = opendnp3.DatabaseSizes(num_binary, 0, num_analog, num_counter, ...)
# the extra points report values like any other point but wire to nothing.
# OpenDNP3 builds the larger response + its CRCs natively. No forged bytes.
Why this and not "invalid index" padding: padding with non-existent points makes the outstation answer with an OUT_OF_RANGE error — a giveaway. Real-but-inert points grow the response cleanly with no error signature. Rig result: device A padded from 214 B to a byte-identical 361 B (matching device B), master decoded all 80 points, 0 resets. The 0.797 device-ID figure is still a trace-feature simulation — closing the fingerprint needs three real devices, but the padding mechanism itself is now proven on hardware.
08

Boundaries & honest limits

What this work does not show, stated plainly, so nothing here is read for more than it proved.

  • The rig outstation is a replay server, not a real device. Native times are replay-fast (~1 ms), not a device's ~16 ms. The rig validates the mechanism, safety, byte-preservation, and TCP health on real hardware — not closure of a real device's size/timing leak. That needs the physical SEL-751 / AB1400 / ION7550.
  • The 40 ms ACK threshold is host/kernel behaviour (Linux delayed-ACK timeout on kernel 6.8), not a protocol guarantee. Other stacks differ.
  • The attacker evaluation is a simulation on trace features, not a capture of the live defended server. It normalizes recorded times; it does not model queueing or measurement noise of a deployment.
  • Bounded normalization does not remove all leakage — the size and ACK-mode residuals above are real and persist.
  • Scope this phase: no byte modification, no CRC recompute, no padding, no forged ACK, no live proxy. The primitive is deliberately conservative.

What's next

  • Byte-preserving response padding to close the size channel (configured-but-unwired points, not invalid indices).
  • Phase-2B: independently delaying the pure ACK and the response (now shown inducible ≥ 40 ms) — needs packet-level control (rig / P4).
  • A real-device run to measure leak-closure end-to-end.
  • Port the validated primitive to P4 / Tofino.
