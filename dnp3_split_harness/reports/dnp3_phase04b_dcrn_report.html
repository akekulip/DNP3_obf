§0 The one-page version

An electric-grid device called an outstation answers polls from a master over a network. Even if the messages are unreadable to an eavesdropper, the shape of the traffic — how big the replies are, how they are cut into packets, how quickly they come back, and whether the network acknowledgement rides along with the reply or arrives separately — is enough to recognise which brand of device is answering. That recognition is called fingerprinting, and it is a privacy leak.

This phase built and tested one defence against the timing part of that leak: a small program, DCRN (Dual-Case Release-time Normalizer), that runs inside the operating-system kernel and controls the exact moment each reply packet is released onto the wire — without changing a single byte of the message. It makes every device's reply appear to take the same amount of time.

The headline DCRN works on real hardware. On a two-machine rig it normalized every device's reply from a device-specific ~16.8 ms to a common target, with zero dropped, retransmitted, or reordered packets and zero bytes changed. It also revealed something important and honest: a fixed single target is not enough — a tiny, unavoidable timing artifact still betrays the device — but a randomized bounded target erases the timing signal. The remaining leaks (packet size, and separate-vs-combined acknowledgement) are deliberately out of this phase's scope.

This report explains, from first principles, every piece: the problem, the idea, what eBPF / tc / EDT / BTF / libbpf are, the actual code, how the rig test ran, what the numbers mean, and what is left. If a term is new, it is defined the first time it appears and again in the glossary.

Part I · The problem

§1 What an eavesdropper can see

DNP3 is a protocol used across the electric power grid so a control centre (the master) can read measurements from field equipment (an outstation) — substation controllers, meters, relays. It runs over ordinary TCP, the same reliable-delivery network protocol that carries web pages.

Imagine someone who cannot decrypt or read the DNP3 messages but can watch the packets go by — a passive observer tapping the wire. What can they still learn? Four things, and none of them require reading the contents:

Size
How many bytes the reply is. Different device models return different-sized replies.
Segmentation
How the reply is chopped into packets — one big packet, or several small ones.
Timing
How long after the poll the reply comes back — a device's "reaction time."
ACK mode
Whether the network acknowledgement comes back on its own or rides along with the reply (explained just below).

Any one of these is a partial fingerprint. Together they are often enough to name the exact device model — which tells an attacker what equipment is deployed and, by extension, how to attack it. This report is about closing the timing channel.

A 30-second TCP primer: what is an "ACK"?

TCP guarantees delivery by having the receiver acknowledge (send an "ACK") for data it received. So when the master sends a poll, the outstation's side of the conversation produces two logically separate things: (1) a bare acknowledgement saying "I got your poll," and (2) the actual DNP3 reply carrying the measurements.

The operating system is allowed to combine those two into a single packet (the ACK "rides along" on the reply — called a piggybacked or combined ACK), or to send the bare ACK first as its own tiny packet and the reply later (a separate ACK, also called a "pure ACK" because it carries no data). Which of these a device does is itself a fingerprint — and it interacts with timing, as we'll see.

Part I · The problem

§3 The rule: don't touch the bytes

The governing constraint for this research line is strict and deliberate:

Invariant No DNP3 field may be modified. No checksum recomputed. No padding added. No packet fabricated. The exact original bytes must reach the master, in order. Formally: if you concatenate the pieces the defence sends, you get back the original reply, byte-for-byte.

This rules out most obvious defences (you cannot pad the reply to a common size, because padding changes bytes). What it leaves open is timing: you can change when a packet is released without changing what it contains. That is the entire manoeuvring room DCRN operates in — and this phase's job was to squeeze it fully.

Part II · The idea

§4 The idea behind DCRN

DCRN's principle is one sentence: hold every reply until a common target time, then release it. If the SEL-751 is naturally ready at 18 ms and the AB1400 at 16.7 ms, and we hold both until, say, 32 ms, then to an outside observer both took 32 ms. The device-specific reaction time disappears.

Two design choices make this real:

Dual-case

The hold must work for both native shapes. For a combined device, there is one packet to hold. For a separate device, there are two — the pure ACK and the later reply — and both must be scheduled so the observer sees a normalized, consistent picture. Handling both shapes in one mechanism is the "Dual-Case" in the name.

Fixed vs bounded target

What common time do we hold to? Two policies were tested:

FIXED
Every reply is held to the same target (32.39 ms, chosen by calibration — see below). Simplest possible.
BOUNDED
Each reply is held to a target randomly drawn from a window [32.39, 42.39] ms. The randomness is per-transaction and independent of the device.

A central result of this phase is that these two are not equally good — and the difference is subtle enough that it only shows up under careful statistical audit. We'll get there in §20–§22. First, the machinery, because you cannot judge the result without understanding how the hold is actually performed.

Where the target comes from 32.39 ms is not arbitrary. It was calibrated from 5,694 real transactions: it sits just above the 99.9th percentile of native "readiness," so almost every reply is naturally ready before the target and can be held back to it. The upper bound 42.39 ms stays far under TCP's ~200 ms retransmission timeout, so holding a packet never risks a spurious resend. (More in §13.)
Part III · The machinery (nothing assumed)

§5 How a packet leaves a computer

To hold a packet, you must intercept it at the right place. When an application (here, the outstation) sends data, the bytes travel down through the operating-system kernel (the privileged core of the OS) and out the network card (NIC). Near the very bottom sits a subsystem called tc ("traffic control") with a component called a qdisc ("queueing discipline") — the thing that decides the order and timing in which queued packets are actually put on the wire.

So the plan is: put a small program at the egress hook that, for each outgoing reply, stamps it with a "do not send before this time." A cooperating qdisc obeys the stamp. But what kind of program can you safely run inside the kernel? That is eBPF.

Part III · The machinery

§6 eBPF: safe code inside the kernel

eBPF (extended Berkeley Packet Filter) is a technology that lets you load a small program into the running kernel and attach it to events — such as "a packet is about to leave via this network card." The program runs in kernel context, at kernel speed, on every packet.

Running arbitrary code inside the kernel would normally be catastrophically unsafe. eBPF makes it safe with a verifier: before the program is allowed to load, the kernel mathematically checks that it cannot crash, cannot loop forever, and cannot touch memory it shouldn't. A program that fails verification is simply rejected. This is why eBPF programs have peculiar rules (no unbounded loops, every memory access bounds-checked) — those rules are what make them provably safe.

eBPF
Small, verified programs that run inside the Linux kernel, attached to events like packet arrival/departure.
Verifier
The kernel's gatekeeper: it proves a program is safe (terminates, no bad memory access) before loading it.
tc / clsact
tc is Linux traffic control; clsact is a special qdisc that provides the ingress + egress attach points for eBPF programs.
JIT
Just-In-Time compilation — the kernel turns the eBPF bytecode into native machine code so it runs at full speed. Our program loads "jited."

DCRN is two eBPF programs sharing state: one on the ingress hook (to notice a poll) and one on the egress hook (to hold the reply). They are written in a restricted subset of C and compiled to eBPF bytecode. You'll see the actual code in §10–§12.

Why in-kernel and not in the app? An earlier phase tried to delay replies from inside the application. The problem: by the time the app acts, the kernel has already decided whether the ACK is separate or combined — so an application delay can accidentally change the ACK mode, creating a new leak. The eBPF egress hook sits below that decision: it can move when a packet leaves without ever altering whether the ACK was separate or combined. That is DCRN's structural advantage.
Part III · The machinery

§7 EDT: delaying a packet without a timer

How do you actually make a packet wait? The naive idea — "start a timer, hold the packet, release it later" — is hard and fragile inside the kernel. Linux provides a far cleaner mechanism: EDT, Earliest Departure Time.

Every packet buffer in the kernel (an skb, "socket buffer") has a timestamp field called skb->tstamp. If you set it to a future time and use a qdisc that honours it — the fq ("fair queue") qdisc — then fq simply will not release the packet before that time. No timer, no holding logic, no risk of losing the packet: you write one number, and the qdisc does the waiting.

skb
"socket buffer" — the kernel's container for one packet as it moves through the stack.
skb->tstamp
A timestamp on the skb. Under EDT it means "earliest time this may depart."
EDT
Earliest Departure Time — the scheme where you set a future tstamp and the qdisc releases the packet at (not before) that time.
fq
The "fair queue" qdisc; it reads skb->tstamp and paces packets accordingly. DCRN requires fq as the root qdisc.

So DCRN's egress program does exactly one write to each reply it decides to hold: skb->tstamp = release_time. fq does the rest. Crucially, the payload bytes are never touched — only the departure timestamp — which is precisely how DCRN honours the "don't touch the bytes" invariant.

Part III · The machinery

§8 Maps: shared memory for the two hooks

There is a coordination problem. The ingress program sees the poll arrive; the egress program, some milliseconds later, must hold the matching reply. These are two separate programs — how does the second one know what the first one saw?

Through an eBPF map: a kernel key–value store that eBPF programs can read and write, and which persists between invocations. DCRN uses two:

dcrn_flows
Keyed by connection. When a poll arrives, ingress stores that flow's target release-deadline here. Egress looks it up to know when to release the reply.
dcrn_ctr
A one-slot counter, incremented per poll, used to draw the per-transaction random target in BOUNDED mode.

For the two programs to share the same maps, the maps are pinned by name — given a stable name in a special kernel filesystem (/sys/fs/bpf) so both attach points bind to the identical map rather than each making its own private copy. (This "pin-by-name" detail becomes important in §17, because two different eras of Linux tooling express it two different ways.)

Part III · The machinery

§9 One decision, three homes

The heart of DCRN is a handful of pure integer functions — pick the target, classify a reverse packet, compute the release time. These live in a single shared C header, phase04b_dcrn_common.h, and are compiled into three places so they can never drift apart:

  1. The eBPF data plane — runs in the kernel on real packets.
  2. A userspace conformance harness — the same C compiled as an ordinary program, run over 43 hand-built cases to check the logic.
  3. A Python reference "oracle" — mirrors the same functions, cross-checked against the C to 0 mismatches.

This is a correctness technique: the risky, hard-to-debug kernel code and an easy-to-test ordinary program run the exact same logic, so a bug is caught in the easy place. When we say "43 cases, 0 mismatch," this is what it means.

Part IV · The implementation, code and all

§10 Ingress: arming a request

When a packet arrives, the ingress program must answer: "is this a DNP3 poll I should react to?" It only arms on a genuine READ request (the routine "give me your measurements" poll), never on setup handshakes or control commands. Here is the real code, annotated:

SEC("ingress")
int dcrn_ingress(struct __sk_buff *skb)
{
    struct hdrs h;
    if (!parse(skb, &h))          // not IPv4/TCP → ignore
        return TC_ACT_OK;
    if (!is_read_request(skb, &h)) // not a DNP3 READ → don't arm
        return TC_ACT_OK;

    struct dcrn_config cc = cfg();  // compiled-in config (FIXED/BOUNDED, target, guard…)
    if (cc.mode == DCRN_MODE_NATIVE)  return TC_ACT_OK;

    __u64 counter = 0;               // per-poll counter (drives BOUNDED randomness)
    __u64 *ctr = bpf_map_lookup_elem(&dcrn_ctr, &zero);
    if (ctr) { counter = *ctr; *ctr = counter + 1; }

    __u64 target = dcrn_select_target_ns(&cc, counter);
    if (!dcrn_target_safe(&cc, target)) return TC_ACT_OK; // unsafe → fail open

    __u64 now = bpf_ktime_get_ns();
    __u64 key = key_master(h.ip->saddr, h.tcp->source);
    struct dcrn_flow f = {};
    f.deadline_ns  = now + target;    // ← the release deadline egress will honour
    f.expected_ack = bpf_ntohl(h.tcp->seq) + h.payload_len;
    f.armed = 1;
    bpf_map_update_elem(&dcrn_flows, &key, &f, BPF_ANY); // store for egress
    return TC_ACT_OK;                 // pass the poll through unchanged
}

bpf/phase04b_dcrn.c — the ingress hook. TC_ACT_OK = "let this packet continue." The program never blocks or edits the poll; it only records a deadline.

Two subtleties worth understanding:

  • Reading the DNP3 type safely. To confirm it's a READ, the code must read a byte deep in the packet — but on the ingress path that data may not be in a contiguous buffer, so it uses the helper bpf_skb_load_bytes() which safely reads across the packet. (A direct pointer read would fail the verifier or read garbage.)
  • The counter is a plain read-then-write, not an atomic add — because the compiler on the dev box (clang 10) cannot use the atomic instruction's return value, and a class-independent counter doesn't need strict cross-CPU atomicity. Small detail, real constraint.
Part IV · The implementation

§11 Egress: classify & stamp

The egress program sees every outgoing packet on the connection and must decide: is this the pure ACK, the actual reply, or something to leave alone? Then it stamps the departure time.

SEC("egress")
int dcrn_egress(struct __sk_buff *skb)
{
    struct hdrs h;
    if (!parse(skb, &h)) return TC_ACT_OK;
    if (bpf_ntohs(h.tcp->source) != DCRN_DNP3_PORT) return TC_ACT_OK; // only outstation→master

    __u64 key = key_master(h.ip->daddr, h.tcp->dest);
    struct dcrn_flow *f = bpf_map_lookup_elem(&dcrn_flows, &key);
    if (!f || !f->armed) return TC_ACT_OK;   // no matching poll → fail open (native)

    int covers = dcrn_ack_covers(bpf_ntohl(h.tcp->ack_seq), f->expected_ack);
    int kind = dcrn_classify_reverse(h.payload_len, h.tcp->ack, h.tcp->syn,
                                     h.tcp->fin, h.tcp->rst, 1, 0, covers);
    if (kind == DCRN_KIND_BYPASS) return TC_ACT_OK;

    int is_separate;
    if (kind == DCRN_KIND_PURE_ACK) { f->pure_ack_seen = 1; is_separate = 1; }
    else { is_separate = f->pure_ack_seen ? 1 : 0; f->response_seen = 1; }

    int miss = 0;
    __u64 now = bpf_ktime_get_ns();
    __u64 rel = dcrn_release_ns(kind, now, f->deadline_ns, is_separate, &cc, &miss);
    skb->tstamp = rel;                // ← the ONLY mutation: the departure time
    return TC_ACT_OK;
}

bpf/phase04b_dcrn.c — the egress hook. The single meaningful side-effect is skb->tstamp = rel. Everything else is reading and classifying.

The classification (dcrn_classify_reverse) is deliberately conservative. A zero-payload packet that is an ACK and covers the request (acknowledges the poll's bytes) is a pure ACK. A payload-bearing packet that covers the request is the RESPONSE. Anything that doesn't fit — a retransmit, a control packet, an ACK that doesn't cover the poll — is BYPASS: left completely alone (fail-open). This conservatism is what keeps DCRN from ever mis-handling traffic it doesn't understand.

Part IV · The implementation

§12 Fixed vs bounded targets — and the "guard"

Target selection is one small function. Read it closely, because the difference between its two branches is the entire FIXED-vs-BOUNDED story:

static __u64 dcrn_select_target_ns(const struct dcrn_config *c, __u64 counter)
{
    if (c->mode == DCRN_MODE_FIXED)
        return c->fixed_ns;                    // same target every time
    // BOUNDED: uniform-ish in [lo, hi] from a seeded hash of the counter
    __u64 span = c->hi_ns - c->lo_ns + 1;
    __u64 h = dcrn_splitmix64(c->seed ^ (counter * 0x9E3779B97F4A7C15));
    return c->lo_ns + (h % span);           // random target, per transaction
}

bpf/phase04b_dcrn_common.h — the target depends only on (mode, seed, counter), never on the device, the size, or the native timing. That independence is later verified statistically.

Now the guard. For a separate device, DCRN schedules the pure ACK to the target and the reply a tiny amount after it — a "guard delta" — so the reply never accidentally races ahead of its own ACK. The release function encodes this:

static __u64 dcrn_release_ns(int kind, __u64 ready, __u64 deadline,
                             int is_separate, const struct dcrn_config *c, int *miss)
{
    __u64 target = deadline;
    if (kind == DCRN_KIND_RESPONSE && is_separate && !c->fifo_reliable)
        target = deadline + c->guard_ns;   // separate reply: +guard after the ACK
    if (ready > target) { *miss = 1; return ready; } // already late → send now (never earlier than ready)
    return target;
}

The guard is small (~0.06–0.2 ms). It is provably necessary for ordering — but, as §20–§22 show, under a FIXED target it also becomes a faint, deterministic tell. That is the phase's key finding.

Remember this A fixed target makes the separate device's reply land a constant ~0.06 ms after the combined devices' (because of the guard). Constant means a classifier can lock onto it. A bounded target adds per-transaction jitter that swamps that 0.06 ms, hiding it. This is why bounded wins.
Part IV · The implementation

§13 Safety & fail-open

A defence that breaks the protocol is worse than no defence. DCRN is built to fail toward "do nothing" (native behaviour) whenever it is unsure:

No matching poll
Egress sees a packet with no armed flow → pass through untouched.
Unsafe target
If the computed target would exceed a safe ceiling (well below TCP's ~200 ms retransmit timeout), don't hold at all.
Already late
If the reply is somehow ready after its target, send immediately — never hold a packet backwards in time.
Unknown packet
Retransmits, control packets, non-covering ACKs → BYPASS.
Byte safety
The only write is skb->tstamp. Payloads are physically never modified.

In the actual campaigns these safeties showed up as clean numbers: across every run, zero retransmissions, resets, duplicate-ACKs, ordering violations, or deadline misses. The reply always arrived, always in order, always identical.

Part V · Proving it on hardware

§15 The rig: three machines

A defence that only works in simulation is not credible. The real test used three physical Linux machines on the lab network:

Hulk
Plays the outstation. Runs the reply server; DCRN is loaded on its egress so its replies are the ones being normalized.
Vision
Plays the master. Sends the polls, and — importantly — captures the traffic. It is the "external observer" whose viewpoint a real attacker would occupy.
gambit
The development box. It compiles the eBPF, deploys to the two rig machines, runs the campaign, and analyses the captures. No DCRN runs here.
Why capture on Vision? DCRN normalizes when Hulk's packets leave. The whole point is what a downstream watcher sees — so the measurement must be taken downstream, on Vision, after the normalized packets have crossed the network. Capturing on Hulk itself would measure the intent, not the effect.
Part V · Proving it on hardware

§16 Gates A, B, C

The validation was staged so a failure would be caught early and cheaply:

Gate A
Capability probe. Does the eBPF object load and pass the kernel verifier on both hooks — on an isolated scratch interface, touching nothing real? This is where the rig's kernel first says yes or no.
Gate B
Dual-case smoke. A small end-to-end run confirming DCRN actually normalizes timing (not silently doing nothing), byte-for-byte identical, clean transport.
Gate C
Full paired campaign. All three conditions (NATIVE / FIXED / BOUNDED) over the same transactions, captured for statistical analysis.

Gates A–C first passed on the dev box (loopback). Then Gate A was re-run on the rig — and that is where the interesting problem appeared.

Part V · Proving it on hardware

§17 The libbpf port — why the rig first said "no"

This section matters because it is a real, instructive engineering problem, not a footnote.

An eBPF object file has to be loaded into the kernel by a loader. Over the years, the Linux networking toolchain (iproute2, which provides the tc command) changed how it loads eBPF and what format of object it expects. There are two eras:

Legacy loader
Older iproute2 has its own built-in eBPF loader. It expects maps declared in an old bpf_elf_map struct format, and needs no type information.
libbpf loader
Newer iproute2 is linked against libbpf, the modern, standard eBPF loading library. It expects maps in a newer "BTF" format and rejects the old one.
libbpf
The standard library for loading and managing eBPF programs and maps. Modern tooling is built on it.
BTF
"BPF Type Format" — compact type information embedded in the object so the loader knows the exact shape of every map and structure. libbpf uses it; the legacy loader doesn't.

The dev box (gambit) runs the legacy tooling. The rig machines run kernel 6.8 with iproute2-6.1.0 linked against libbpf 1.3.0 — the modern loader. So the object that loaded perfectly on gambit failed on the rig with a blunt error:

ERROR: opening BPF object file failed
Unable to load program

The fix was a clean, minimal port: keep one source file, but express the two map definitions in both formats behind a compile-time switch. The legacy build is unchanged; a new build flag -DDCRN_LIBBPF_MAPS selects the modern format (and -g emits the BTF the new loader needs):

#ifdef DCRN_LIBBPF_MAPS
/* modern libbpf format: BTF ".maps", pinned by name so both hooks share state */
struct {
    __uint(type, BPF_MAP_TYPE_LRU_HASH);
    __type(key, __u64);
    __type(value, struct dcrn_flow);
    __uint(max_entries, 4096);
    __uint(pinning, LIBBPF_PIN_BY_NAME);
} dcrn_flows SEC(".maps");
#else
/* legacy iproute2 internal-loader format (the dev box) */
struct bpf_elf_map SEC("maps") dcrn_flows = {
    .type = BPF_MAP_TYPE_LRU_HASH, .size_key = sizeof(__u64),
    .size_value = sizeof(struct dcrn_flow), .max_elem = 4096, .pinning = 2,
};
#endif

bpf/phase04b_dcrn.c — one source, two map ABIs. The decision logic is byte-identical between them; only the way maps are declared to the loader differs.

The rebuilt libbpf object was shipped to Hulk and re-probed. Gate A on the rig then passed:

kernel=6.8.0-134-generic
tc_version=iproute2-6.1.0, libbpf 1.3.0
--- verifier: ACCEPTED on ingress + egress ---
...id 72 name dcrn_ingress ... jited
...id 76 name dcrn_egress  ... jited

Gate-A rig evidence. "ACCEPTED … jited" = the kernel verified the program and compiled it to native code. The port worked.

The transferable lesson eBPF object portability across kernel/tooling versions is not automatic. The same source can need two different map declarations depending on whether the target uses the legacy or the libbpf loader. Now recorded in project memory so the next rig doesn't rediscover it.
Part V · Proving it on hardware

§18 How the campaign actually ran

Orchestrating two machines over SSH surfaced a handful of small but real gotchas, each solved:

  • The reply server is one-shot — it serves a single poll session then exits. So the driver restarts it before every run, while one packet capture spans all runs.
  • Capturing needs care over SSH — the packet filter lives inside a small helper script on Vision, so no fragile quoted filter string has to survive the SSH command line.
  • A safety watchdog is armed on Hulk before each campaign: even if the orchestration were to die mid-run, it force-restores Hulk's network interface after 20 minutes, so the shared lab machine can never be left in a modified state.
  • Every privileged action is transient — the rig password is piped to sudo for that one command and never written anywhere.

Result: three conditions, five runs each, all five successful, on both the dev-box loopback and the two-machine rig. On completion Hulk's interface was verified back to its default state, with no leftover DCRN and no orphan processes.

Part VI · Results

§20 The pre-rig audit — where the truth comes out

Before trusting the rig, a seven-point statistical audit was run. Its job was to be adversarial: to find any way the "defended" traffic still leaks. Three of its checks tell the whole story.

What the "attacker" is

The attacker is a machine-learning classifier (a random forest) trained to guess which of the three devices produced a transaction, using only chosen features. Its score is balanced accuracy: 1.0 = perfect identification, and 0.333 = pure chance (there are three devices). Lower is better for the defence. Every score below uses a leakage-safe split (train and test on different sessions) and is averaged over 100 repeats, with a confidence interval.

Check 1 — feature purity

A subtlety the audit insists on: the feature "time to the first reverse packet" is not a pure timing feature. For a separate device that first packet is the near-instant pure ACK; for a combined device it's the reply ~16 ms later. So its value encodes the ACK mode, disguised as timing. The audit therefore reports the pure timing feature — time to the actual response — separately, and only that carries the "did we fix timing?" verdict.

Check 2 — scheduler error by device

The audit measures, per device, how far each release lands from its intended target. Under FIXED it found the separate device (SEL-751) lands a consistent ~0.06–0.19 ms later than the combined ones — the guard delta from §12 — and a permutation test confirms this is device-correlated (p = 0.0002). In plain terms: the fixed policy accidentally creates a brand-new, tiny, but reliable timing tell.

Part VI · Results

§21 The two-host rig — does it survive real hardware?

The open question the loopback audit raised: the FIXED residual is only ~0.06 ms. On a real network, with real jitter, wouldn't that wash out? The rig answers it directly. The pure-response-timing attacker, loopback vs rig:

The verdict is unambiguous and identical to loopback: the fixed guard residual survives real switched-path jitter (FIXED = 0.740, above chance, essentially tied with native's 0.731), while bounded closes the timing channel on hardware (0.289, its confidence interval straddling chance). And the bounded target was confirmed statistically independent of the device (permutation p = 0.869).

Everything else held on hardware exactly as designed: per-device pinning to target, byte-identical replies, and 0 retransmissions / resets / ordering violations / deadline misses across all 292 transactions. The mechanism is real, not a simulation artifact.

Part VII · Scope & what's next

§23 What this proves — and what it doesn't

Proven

  • DCRN normalizes reply timing for both native ACK shapes, on real hardware, byte-for-byte, with clean transport.
  • A bounded-random target reduces the timing-only fingerprint to chance; a fixed target does not.
  • The mechanism is safe-by-default (fail-open) and left the shared rig untouched afterward.

Not claimed (honest limits)

  • Size and ACK mode still leak. The "everything together" attacker stays ~0.99 — DCRN is a timing normalizer only. Size is out of the byte-preserving scope; ACK mode is a separate primitive (an earlier phase).
  • Modest sample. The rig used 5 runs per condition (~90–114 transactions), so its confidence intervals are wider than loopback's. A higher-repetition rerun is recommended.
  • Tested workload only. READ-only, single outstanding poll, no packet loss, 1 Gb management path — not the 25 Gb switched data plane, and not real device hardware (replayed captures).
Part VII · Scope & what's next

§24 Next: the Tofino question

The next phase is a feasibility study: can DCRN's timing normalization be moved from a software eBPF program into a programmable switch — specifically an Intel Tofino, which runs the P4 data-plane language — so the defence lives in the network fabric at line rate instead of on the endpoint?

The open tension, already flagged in earlier feasibility notes: DCRN's core move is holding a packet for milliseconds (EDT), and a Tofino switch is deliberately built not to buffer packets for that long — it is a wire-speed forwarding pipeline. So the research question is whether the timing normalization can be re-expressed in a form the switch can do (rate shaping, scheduled dequeue, or a hybrid with a small buffer), or whether the "decide" half can go to the switch while the "hold" half stays at the edge. That, plus the size and ACK-mode residuals, is the agenda when this work resumes.

§ Glossary

DNP3
A protocol used in the electric grid for a master to read/control field outstations, here running over TCP.
Master / Outstation
The controller that polls (master) and the field device that answers (outstation).
Fingerprinting
Recognising which device model produced traffic from its observable shape (size, segmentation, timing, ACK mode).
Passive observer
An eavesdropper who only watches packets, without injecting or decrypting.
TCP / ACK
The reliable transport; an ACK is a receiver's acknowledgement of received bytes.
Pure / separate ACK
A bare acknowledgement packet carrying no data, sent before the reply.
Combined / piggybacked ACK
The acknowledgement carried inside the reply packet.
DCRN
Dual-Case Release-time Normalizer — this phase's defence.
eBPF
Verified programs that run inside the Linux kernel, attached to events like packet egress.
Verifier
The kernel component that proves an eBPF program safe before loading it.
tc / qdisc / clsact
Linux traffic control; the queueing discipline that paces packets; the qdisc providing eBPF hook points.
EDT / skb→tstamp / fq
Earliest Departure Time; the per-packet timestamp; the fair-queue qdisc that releases packets at that time.
Map (eBPF)
A kernel key–value store shared between eBPF programs; DCRN uses it to pass a flow's deadline from ingress to egress.
Pin-by-name
Giving a map a stable name in /sys/fs/bpf so separate programs bind the same map.
libbpf / BTF
The modern eBPF loading library; the type-information format it needs. Newer tc uses these; the legacy loader doesn't.
JIT / jited
The kernel compiling eBPF bytecode to native machine code for full-speed execution.
Balanced accuracy
An attacker score corrected for class sizes; 0.333 = chance for three devices, 1.0 = perfect identification.
Guard delta
The tiny extra delay DCRN puts between a separate device's ACK and its reply to keep ordering; a residual tell under FIXED.
Tofino / P4
A programmable switch chip and its data-plane language — the target of the next feasibility phase.
