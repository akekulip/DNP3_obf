# Attacker-Side Classification Evaluation (DNP3 Timing Obfuscation)

Generated by `attacker_eval.py` (seed 42). Deterministic; outputs overwritten each run.

## Setup

- Input: `reports/ack_trace_characterization.csv` -- 11494 device-specific transactions after excluding the shared reference outstation 10.0.0.2.
- Classes: AB1400, ION7550, SEL751 (device-type fingerprinting attack).
- Per-device transaction counts: {'ION7550': 4798, 'SEL751': 4298, 'AB1400': 2398}.
- **Split scheme (headline):** capture-level. Train on each device's base PCAP (AB1400.pcap, ION7550.pcap, SEL751.pcap); test on its larger "L" PCAP (AB1400L.pcap, ION7550L.pcap, SEL751L.pcap). Every transaction from a capture stays on one side of the split, so adjacent packets from the same flow cannot leak across train/test. There are 6 flows (one per PCAP), so a random row split would leak heavily; this is why it is avoided.
- **Robustness split:** leave-one-PCAP-out GroupKFold (6 folds), predictions pooled.

Chance (majority-class) accuracy on the test set = 0.400.

Reading the table:

- **size_only and ackmode_only are identical across every column** -- the timing defense cannot touch response size or ACK mode, so these residual channels are unchanged by construction.
- **timing_only** accuracy does NOT drop under the defense (~0.80 throughout). The surviving timing signal is the ACK-mode-linked one -- SEL751's pure transport ACK (`req_to_ack` ~4 ms) separates it regardless of response delay -- while the two combined-ACK devices were never well separated by latency to begin with (next table). Response-delay normalization thus removes little device-ID *accuracy* here even though it does reshape the response-time distribution (detect-the-defense, section 3).
- **uniform_10_15** barely moves any number: the devices' native response times (~16 ms) already exceed the 15 ms ceiling, so `max(native, U(10,15)) ~= native`. A normalization floor must exceed the native latency to obfuscate anything.

### Where timing carries unique device-ID signal (and what the defense does to it)

Response SIZE separates ION7550 and ACK MODE separates SEL751; the ONLY device-ID signal carried uniquely by response *latency* is between AB1400 and ION7550 (both COMBINED-ACK, identical size support otherwise). Isolating that pair on timing features (balanced accuracy, chance = 0.5):

| Setting | balanced acc | raw acc | majority baseline |
|---|---|---|---|
| native | 0.497 | 0.661 | 0.667 |
| uniform_10_15 | 0.497 | 0.661 | 0.667 |
| uniform_15_25 | 0.500 | 0.667 | 0.667 |
| constant_25 | 0.500 | 0.666 | 0.667 |

Two honest readings: (i) even NATIVELY the two combined devices are essentially inseparable by latency (balanced acc 0.497, at the 0.5 floor) -- the response-time channel simply does not carry device identity between them in this trace; (ii) under `constant_25` the two devices' timing feature vectors become provably identical (every response floored to 25 ms, ACK piggybacked), so balanced accuracy sits exactly at the 0.5 floor (0.500). The defense erases the (small) timing signal it targets; it is not the reason overall device-ID stays high.

## 5. What this shows / what it does NOT

**Shows:**

- A real device fingerprint exists: native all-features device-ID accuracy 0.897 >> chance 0.400, and it generalizes across a capture-level split (train base PCAP -> test a disjoint, larger L PCAP; leave-one-PCAP-out is more pessimistic at 0.722).
- The fingerprint is carried mainly by response SIZE (separates ION7550) and ACK MODE (separates SEL751), not by response latency -- so this trace's fingerprint is largely in channels the timing defense cannot touch.
- Where response latency *does* carry unique identity (AB1400 vs ION7550), bounded normalization erases it: under the constant-25 policy the two devices' timing vectors become identical and balanced accuracy sits at the 0.5 floor.
- The Phase-1 defense reshapes the response-time distribution measurably and is detectable (floor + quantization signature), strongly so for the constant-target policy.

**Does NOT show / honest residuals (per brief section 12 -- do not overclaim):**

- This is a **SIMULATION on trace features**, not a capture of the live defended server. It normalizes recorded `req_to_resp_ms` (and re-derives dependent timing features); it does not model queueing, RTO interaction, or measurement noise of a real deployment.
- **Bounded normalization does NOT remove all leakage.** Two residual channels survive:
  1. **Size:** `resp_size` is {37,54} for AB1400 and SEL751 but {37,61} for ION7550. Size separates ION7550 yet cannot split AB1400 from SEL751, and the timing defense never touches size -- so `size_only` accuracy is identical native vs defended (= 0.500). There is no byte-preserving DNP3 padding in this phase, so this size leak persists.
  2. **ACK mode / ACK timing:** SEL751 is the only SEPARATE-ACK device; its pure transport ACK (`req_to_ack` ~4 ms) is not held by a byte-preserving response delay, so `ackmode_only` accuracy is also invariant to the timing defense (= 0.800). This motivates a dedicated ACK-timing normalization (brief option C), which this response-delay primitive does not provide.
- Because those residuals carry most of the class separability here, **all-features device-ID stays high even after timing normalization** (uniform_15_25 = 0.900, constant_25 = 0.900). The timing defense should be framed as closing the **timing channel specifically**, not as a full device-anonymization defense.
- Only 3 device classes from 6 captures; bootstrap CIs treat rows as independent and therefore understate uncertainty (rows within a capture are correlated).
