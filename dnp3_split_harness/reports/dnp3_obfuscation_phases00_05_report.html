The whole project in one paragraph

Electric-grid field devices speak a protocol called DNP3 over ordinary TCP/IP. Even without reading the message contents, the shape of the traffic — reply size, how it is split into packets, timing, and a subtle TCP habit called the ACK mode — can reveal which brand/model of device is answering, which tells an attacker which weaknesses to try. Across six phases we (1) proved this fingerprint is real by measuring three captured device profiles, and (2) showed that where we control the responding socket (a replay, decoy, or software-controlled outstation), a technique called socket coalescing removes the strongest categorical tell — the ACK mode — on the live network, without changing any DNP3 byte, dropping any packet, or breaking the connection. The honest limits: this is not yet a transparent defense for an unmodified physical device, and the traffic remains fingerprintable — most stably by response size, and possibly by other channels we did not test.

Foundations · no prior knowledge assumed

What is DNP3, an outstation, and a “master”?

DNP3 (Distributed Network Protocol 3) is a language electric utilities use so a control center can talk to field equipment — breakers, meters, relays. Think of it as the “texting language” of the power grid. It usually runs over TCP/IP (the internet’s transport) on network port 20000.

The two roles

Master = the control center; it asks questions (“report your status”).
Outstation = the field device that answers. In our work the outstation is what we’re protecting, because its replies carry the fingerprint.

A “transaction”

One request from the master + the outstation’s response. We break every capture into these request→response pairs and study them one at a time. A typical poll: master says READ, outstation replies with current measurements.

A “packet capture” (PCAP) is a saved recording of every packet on a wire, like a wiretap log. This project is grounded in six real PCAP recordings of three real devices (~73,500 packets), plus controlled replays we run ourselves. The tool that reads PCAPs is tshark (command-line Wireshark).

Foundations

The threat — and exactly where the observer sits

Our attacker is a passive observer: they can watch packets but not change them, and they do not need the message contents. The question is whether traffic shape alone reveals which device is answering.

Be precise about the threat model — it changes everything “Fingerprinting” only makes sense once you fix where the observer is and what they can already see. On a plaintext DNP3 LAN, an eavesdropper can often already read addresses, function codes, object/point counts — so traffic-shape obfuscation alone does not hide the device; it is one layer among several. The traffic-shape tells matter most when payload inspection is unavailable, deliberately excluded from the model, or blocked by an encryption layer (TLS/IPsec/VPN) that still leaves per-flow metadata (packet sizes, counts, timing, TCP behaviour) visible. Which TCP headers survive, and whether one visible flow maps to one device or to a gateway aggregating many, depends on that deployment. This report studies the traffic-shape channel specifically; it does not claim to hide a device on a fully-readable plaintext LAN.

Foundations · the constraint that makes this hard

The hard rule: change the silhouette, never the message

The whole project obeys one non-negotiable rule: every byte the outstation sends must reach the master unchanged. We may change how bytes are packaged or when they leave — never which bytes.

The governing spec (docs/implementation_guide.md) states it bluntly:

# The phase rule, verbatim from the spec:
No CRC recompute.  No DNP3 field/length modification.  No random padding.
No P4.  No proxy/MITM.  No control commands.

# The invariant every experiment must satisfy:
b"".join(chunks) == original_response_bytes   # the pieces re-join to the exact original

Why so strict? This is safety-critical grid equipment. Altering a byte could fail a checksum, cause the device to reject the message, or show an operator wrong data. So our defenses are reversible re-packaging, not edits — which is what makes the results trustworthy.

The building block: “CRC-boundary splitting”

A DNP3 message is already built from blocks, and every block already ends with a 2-byte CRC (a checksum). Our splitter cuts the byte stream only at those existing boundaries, so each piece still ends on a checksum that was already valid; nothing is recomputed, and the master glues the pieces back into the identical message. Drag the slider — the re-joined bytes are always identical.

Important: splitting is a shaping primitive, not size hiding CRC-boundary splitting reshapes individual packet sizes, but it does not hide the total response size — an observer can simply add up the pieces. It can even convert a size tell into a packet-count tell (more bytes → more chunks). The project’s own analysis notes that aligning cuts to CRC boundaries is an auditability choice, not a TCP requirement, and that what appears on the wire also depends on pacing and the capture vantage point. Treat splitting as a shaping tool, not complete size obfuscation.
Foundations · the star of the show

Separate ACK vs combined ACK — the tell we ultimately erase

TCP requires the receiver to acknowledge (“ACK”) data. A device can do this two ways, and which way it habitually chooses is a fingerprint.

Separate ACK — 3 packets

The outstation first sends a tiny pure ACK (“got your request”, zero data), then the actual response. An observer sees three packets and a distinctive gap. This is how the SEL-751 profile behaves.

Combined ACK — 2 packets

The outstation sends the acknowledgement piggybacked on the response — one packet does both jobs. An observer sees only two packets. This is how AB1400 and ION7550 behave.

What decides it? A TCP mechanism called the delayed-ACK timer (~40 ms on Linux), plus socket state such as TCP_QUICKACK. Press the toggle to watch both modes on a simulated wire.

Interactive · the two ACK modes on the wire

A subtlety your advisor may probe — and we do not overclaim It is tempting to say “separate = the answer took longer than the 40 ms timer.” That explains our tested Linux replay server, but not the physical devices: their median reply times are almost identical (SEL-751 ~16.1 ms, AB1400 ~16.2 ms, ION7550 ~16.0 ms), yet only SEL-751 is separate. So SEL-751’s separate ACK is not explained by a longer reply time — it comes from that device’s own TCP-stack behaviour (quickack-like state, implementation-specific ACK heuristics, or socket policy) which we did not open up. We report the what (SEL-751 is separate) precisely, and do not invent a why.
The key idea for Phase 05 A separate ACK is a loud, categorical device tell. Our Phase-05 defense makes a controlled endpoint look combined by owning the socket and writing the reply inside the delayed-ACK window so the kernel naturally piggybacks — no packet forged or dropped.

Deep dive (requested)

The delay mechanism & release policy, in detail

“Delaying” a reply sounds trivial, but doing it safely on safety-critical grid traffic is the whole engineering problem. Here is exactly how the scheduler in timing_policy.py decides when each reply leaves.

1 · The core formula

The scheduler never “adds jitter.” It computes an absolute release time and waits until then:

actual_release = max( response_ready , request_received + target_delay )
#                     ^^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                     never before the   never before the common target time
#                     bytes actually exist

The max(…) encodes two promises at once: (a) correctness — we can never send before the outstation has actually produced the bytes; and (b) obfuscation — we hold a too-fast reply until the common target so its native speed is hidden. If the reply is already slower than the target (a “native tail”), the max lets it through immediately — we never make traffic slower than it truly is, and we never speed it up (impossible — you can’t send bytes before they exist).

2 · Where target_delay comes from — and why it leaks nothing

The single most important policy rule: the target is drawn from a distribution that is independent of everything about the device. If the delay depended on device identity, request or response size, content, database size, or native ready-time, it would re-encode the very fingerprint we’re trying to erase.

Modetarget_delayEffect on the wire
native0 (no hold)Wire-identical to no defense — a control baseline
fixeda constant, e.g. 25 msEvery reply appears at the same time (tight distribution)
boundedUniform(min,max), e.g. 20–30 ms, from a seeded RNGReplies spread over a fixed window, unrelated to the device

The random draw uses a deterministic seed so a run is reproducible, but the seed is a function of (run, config, repetition) only — never of the transaction’s size or type. (Getting this wrong is exactly the seed bug Phase 02 caught and fixed.)

3 · The safety rules that wrap the formula

A hold that is too long, or applied to the wrong kind of message, could hurt a live control system. The policy therefore enforces several guardrails, and fails open — if anything is unsafe or uncertain, it delivers the reply natively rather than holding it:

Per-flow FIFO order

Replies within one TCP connection are never reordered — they leave in the order they arrived, just later.

Absolute-deadline waiting

It waits until a target clock time, not “sleep N ms,” so scheduling jitter doesn’t accumulate.

RTO-safe bound

The target must stay below the master’s TCP retransmission timeout (measured ~211 ms here) — otherwise a hold could trigger a retransmission. Safe holds are tens of milliseconds, far under that.

Queue-depth limit & bypass

If too many replies queue, or the target is flagged unsafe, or the function code is a control/unsupported type, the reply bypasses the scheduler and goes out natively. Every bypass is counted and reported.

The delay policy and the ACK mode are coupled There is a second, subtler bound. A hold also has to stay below the ~36–40 ms delayed-ACK transition (characterized next, on the tested Linux server) — because if you hold a combined-mode reply past that window, the kernel emits a standalone ACK first and you’ve accidentally created a separate-ACK tell. That is why Phase 02’s targets (20–25 ms) sit deliberately below both the RTO-safe bound and the ACK-separation window. The two policies — timing normalization and ACK-mode preservation — must be designed together.

4 · A different “delay” in Phase 05: socket coalescing

Phase 05’s defense is also, at heart, about when the reply is written — but the goal is inverted. Instead of holding the reply to a target, we ensure the reply is written inside the delayed-ACK window and we don’t force TCP_QUICKACK, so the kernel piggybacks the ACK onto the reply (combined). No artificial delay is added; the policy is simply “own the socket, answer within the window, don’t force a quick ACK.” It works only while the reply is ready within the window — a slow reply cannot be coalesced, which is a real limitation we return to in Phase 05.

The key findings

  • On the tested server, the separate-ACK transition is probabilistic around 36–40 ms: 0% separate below ~35 ms, rising 1% → 100% between 36 and 40 ms.
  • TCP_QUICKACK forces a separate ACK even at low delays — so ACK mode is controllable from user-space software.

Scope of this threshold — do not over-generalize The 36–40 ms figure characterizes this specific setup: a loopback replay server on Linux 5.15 with the tested application/socket configuration. It does not establish why each physical device chose its native ACK mode, and it may differ on other kernels, NICs, or stacks. Accurately stated, this phase identifies application-write timing and QUICKACK state as effective levers in the tested Linux configuration — not a universal law.
Why this de-risks Phase 02 and sets up Phase 05 It shows Phase 02’s 20–25 ms targets sit safely below the transition, so normalizing timing doesn’t accidentally create a separate-ACK tell — and it reveals the lever Phase 05 uses: answer inside the window → combined; force quickack → separate.

04

Re-timing an existing ACK (a scoped kernel prototype)

Conditional Pass

A harder question: for a device that already emits a separate ACK, can we re-time that ACK and the response independently, deep in the network stack, without forging or dropping anything?

What was done — and its exact scope

Ordinary programs can’t hold back an ACK the kernel already decided to send, so the phase used eBPF — tiny sandboxed programs the Linux kernel runs on the network path — at the packet-exit point (tc egress), with EDT (“Earliest Departure Time”): stamp each packet with when it may leave, and let the kernel’s fq scheduler enforce it. The work happened in two steps: first a feasibility analysis (design only), then a scoped eBPF prototype that was actually compiled, loaded, and run — the repository contains the program (ebpf_prototype/ack_edt.c), the compiled object (ack_edt.o), the loader (run_prototype.sh), and a result record.

eBPF / tc egress / EDT / fq, in plain terms: a programmable traffic light at the network exit. eBPF is the little program; tc egress is where it sits; EDT writes a “green-light time” on each packet; fq holds the packet until then. Loading eBPF needs administrator (root) privileges, so the PI ran it.

Two honest caveats on this phase (1) It is a narrow prototype, not a product. It runs on a loopback single-egress simplification, covers only the gap-normalization mode for separate-mode traffic, and does not include the full production classifier/scheduler, the other planned modes, a two-NIC bridge version, or a real-device run — hence Conditional Pass. (2) The capability boundary is the real lesson: you can re-time a separate ACK that already exists, but you cannot turn a combined reply into a separate ACK without forging a packet — which the “no synthesis” rule forbids. So this mechanism normalizes timing but cannot by itself conceal the ACK mode or the reply size; a fair attacker test confirmed re-timing left the fingerprint essentially intact.

Verdict: Conditional Pass. The core re-timing mechanism is proven on the wire as a scoped prototype, but it does not defeat the fingerprint — which is exactly what motivates Phase 05’s simpler, endpoint-side approach.

05

Erasing the ACK-mode tell — the payoff

Pass scoped, endpoint-controlled

Where we own the answering socket (a replay/decoy/software-controlled outstation), we make a separate-ACK endpoint look combined the safe way: don’t force quickack, and write the reply inside the ~40 ms window so the kernel piggybacks the ACK. No forging, no dropping. Then we measure, with a real attacker classifier on captured defended traffic, how much of the fingerprint that erases.

Read this before the results — the scope boundary Socket coalescing requires control of the responding socket. It applies to replay servers, decoys, honeypots, emulated outstations, and potentially a modified software outstation. It does not currently protect a black-box physical SEL-751 / AB1400 / ION7550 whose TCP stack and application cannot be changed. Concretely: we demonstrated an endpoint-cooperative defense; transparent protection of an unmodified physical outstation remains unresolved.

The mechanism: “socket coalescing”

# Undefended (mimics a separate-ACK endpoint like the SEL-751 profile):
server.setsockopt(TCP_QUICKACK, 1)   # force an immediate standalone ACK

# Defended (socket coalescing):
# ...do NOT set quickack, and write the response within the delayed-ACK window...
conn.sendall(response_bytes)         # kernel piggybacks the ACK -> combined, zero drops

What the “devices” in these tests really are The defended experiments are a profile-derived replay of selected measured observables through a common TCP stack — they reproduce each device’s captured DNP3 bytes, response sizes, selected total timing, and categorical ACK mode. They do not reproduce each physical device’s full TCP stack (its own pure-ACK timing, TCP timestamps, congestion-window and window-update behaviour, retransmission dynamics). So this is not a faithful emulation of the SEL/AB/ION stacks — it is a controlled reproduction of the specific observables the classifier uses.

Byte-preservation & TCP health

Across every condition on both loopback and the two real servers: 2160/2160 replies byte-identical, 0 retransmissions, 0 resets, 0 duplicate ACKs within established sessions. The separate-ACK fraction moved 100% → 0% with no packet loss.

Complete-response check

Because size is the surviving tell, we verified we replayed the complete reply, not just its first packet: all 720 selected transactions are single-TCP-segment, and the source reply’s byte-hash equals the replayed reply’s. The code also handles multi-packet replies correctly in general (unit-tested).

Limits your reviewer will (rightly) ask about Sample & tails: the eval used the first 120 transactions per capture. Coalescing only works when the reply is ready within the window — a rare slow reply (recall ION7550’s ~72 ms outlier) cannot be coalesced, so slow-tail transactions are exactly the cases most likely to leak; a full evaluation should include all eligible transactions, the slow tail, and a coalescing-failure rate. Connection start: we exclude the first transaction of each TCP session (a new Linux connection begins in a quick-ACK state), so the claim is steady-state normalization; a new connection or reconnection may still leak a separate ACK — operationally meaningful in OT networks with reconnects. Statistical independence: the rig has one base and one L capture per device per condition, with many correlated transactions inside each — so the ~357-transaction test is not 357 independent experiments; publication-grade evidence needs multiple independent runs and grouped (leave-one-run-out) splitting.

Verdict: Pass, with scoped limitations. The ACK-mode tell is erased on the wire, byte-preservingly, on real hardware, for an endpoint we control. What remains — the size tell and other untested channels, physical-device behaviour, connection-start behaviour, and an in-line version for devices we don’t control — are honestly-labelled future lines, not failures of this phase.

The bottom line

What Phase 00–05 establishes — and what it doesn’t

Established (proven)

  • The device fingerprint is real and measured on three captured device profiles.
  • On a controlled responding endpoint, socket coalescing normalizes the ACK mode (separate→combined) on the live wire — loopback and two real servers.
  • It is byte-perfect, drops zero packets, and keeps TCP healthy.
  • It measurably reduces classification: the ACK-mode tell drops to pure-guessing (mode_only 0.667→0.333).
  • Timing can also be normalized for combined replies (Phase 02); a separate ACK can be re-timed in-kernel as a scoped prototype (Phase 04).

Not established (deferred / untested)

  • Full anonymity — joint classification stays at 0.756 (0.681 with timing), far above 0.333 chance.
  • Behaviour of the physical devices under the defense (ours are profile-derived reproductions).
  • A safe in-line version for outstations whose socket we don’t control; a Tofino hardware version.
  • Reply-size normalization — the dominant stable residual — a separate, byte-changing line.
  • Other possible residual channels (below) that we did not test.
“Only size remains” would be an overclaim Size is the dominant stable residual in the evaluated feature set — it explains ION7550’s persistent separation. It is not proven to be the only possible tell. Methodology

How we kept it honest (the parts that make it defensible)

Leakage-controlled ML test

We train on one capture and test on a different one of the same device (“capture-level split”), so the model can’t win by memorizing adjacent transactions. We report balanced accuracy against the correct 0.333 chance line, plus confusion matrices and per-feature variances. Caveat: the rig has one run per condition with correlated transactions inside each stream — better than a random split, but not yet multi-run, grouped, leave-one-run-out evidence.

Measured vs projected vs blocked

Every result is labelled by how it was obtained. A projection is never written up as a measurement; a blocked step is marked blocked, not quietly skipped. Phase 00 exists partly to enforce this.

Human spot-check gates

Software classifications were confirmed by a person opening a selected worksheet of packets in Wireshark — 13 of 13 agree (a spot validation of the extractor logic, not all 22,988 transactions). No phase advances itself (next_phase_allowed = false until a human authorizes).

Reproducible by construction

Every run is stamped with a folder, a SHA-256 fingerprint of inputs/outputs, the exact commands, the git commit, the seed, and tool versions. The Phase-01 analysis reproduced its normalized transaction tables and hashes byte-for-byte across two independent runs (timing PCAPs naturally differ in timestamps/ports).

The most important honesty caveat Our three “devices” in the defended experiments are a profile-derived replay of selected measured observables through a common TCP stack — not the physical units. That is why a physical-device test is the one remaining external validation. Saying this clearly is what makes the rest credible.
Reference

Glossary — every term, in one place

Protocol & roles

DNP3: the grid’s control protocol, over TCP port 20000.
Outstation: the field device that answers (what we protect).
Master: the control center that asks.
Transaction: one request + its response.
PCAP: a saved recording of network packets.

TCP behaviour

ACK: a TCP “I received it” acknowledgement.
Pure / separate ACK: a standalone ACK packet with no data.
Combined ACK: an ACK piggybacked onto the reply (one packet).
Delayed-ACK timer: TCP’s ~40 ms wait that (with socket state) decides which happens.
TCP_QUICKACK / TCP_NODELAY: socket switches; quickack forces a separate ACK.
RTO: TCP’s retransmission timeout (~211 ms here); holds must stay under it.

Our mechanisms

CRC-boundary splitting: re-chopping a reply on existing checksum boundaries, bytes intact.
Timing normalization: releasing every reply at a common target time (Phase 02).
Socket coalescing: answering inside the delayed-ACK window so the ACK piggybacks (Phase 05).
eBPF / EDT / fq: in-kernel re-timing of packets that already exist (Phase 04).

Evaluation terms

Fingerprint: identifying the device from traffic shape.
Feature group: a set of tells (mode_only, size, timing, all).
Capture-level split: train on one capture, test on another.
Balanced accuracy / chance = 0.333: fair score vs. one-in-three guessing.
Constant / non-discriminating: a feature identical for everyone — carries no information.
