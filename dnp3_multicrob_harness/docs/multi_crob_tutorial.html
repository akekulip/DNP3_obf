00Orientation

Why any of this matters

The bigger project is about hiding what a power-grid device looks like on the wire. This piece asks a narrower, prerequisite question — and answers it with hard evidence.

Picture the control system of an electrical substation. A master station continually talks to field devices called outstations — the boxes wired to breakers, relays and meters — using a protocol named DNP3. Most of that traffic is the master reading measurements. Occasionally, the master sends a control: "open that breaker," "latch that output on."

Our supervising question was deceptively small:

the question

Can a single DNP3 SELECT/OPERATE transaction carry several valid control objects at once — targeting several output points — and will the outstation actually process them all?

Why care? Because ordinary control messages are tiny and predictable, and predictability is exactly what a fingerprinter exploits. If the protocol legitimately allows packing multiple controls into one message, that's a native lever for varying control-message structure later. But before anyone builds on that idea, the behaviour has to be proven, safely, in software. That proof is what this note documents — and, honestly, the more interesting half is the fight it took to get a clean result out of the tooling.

This is validation, not obfuscation No physical device is ever touched Nothing in the existing read/replay path changed
01Top of the funnel

What is DNP3?

DNP3 (Distributed Network Protocol, version 3) is the language substations speak. It is a request/response SCADA protocol: a master asks, an outstation answers. In our lab it rides over plain TCP on port 20000.

the master

Asks & commands

The station computer. It polls for data ("give me all your Class 0 points") and, rarely, issues controls ("operate output 3"). In our rig this is the host Vision, DNP3 link address 1.

the outstation

Answers & acts

The field device. It holds a small database of measurements and output points, replies to reads, and executes controls it accepts. In our rig this is Hulk, link address 10.

Two vocabulary rules we hold to for the rest of this note, because mixing them up is the classic beginner error:

  • SELECT and OPERATE are function codes — verbs the application layer understands.
  • A CROB is an object — a noun the verb acts on. It is not a function code. (We'll meet it properly at stop 06.)

A CROB latching an output "on" is a control code applied to one binary output point — not a rack of physical latches. Keep that picture; it prevents a lot of confusion downstream.

02Narrowing

DNP3 is a stack of three layers

A DNP3 message isn't one blob — it's wrapped in three layers, each with its own job. To reach the control object, our bytes travel down through all three. Open each layer:

L1 Data Link Layer framing · integrity

Chops the byte stream into link frames. Every frame begins with the two start octets 0x05 0x64, carries a LEN byte, source/destination link addresses, and — crucially for the wider project — a CRC every 16 bytes. Those built-in CRC block boundaries are exactly where the harness's existing "CRC-boundary split" cuts the stream without recomputing anything.

L2 Transport Function segmentation

A single byte per frame with FIR (first), FIN (final) and a rolling sequence. It lets a long application message be split across many link frames and reassembled in order. A big read response is naturally many frames stitched back together here.

L3 Application Layer meaning

Where the intent lives: an application control byte (FIR/FIN/CON/UNS + a sequence number), a function code (READ, RESPONSE, SELECT, OPERATE…), and — in responses — two IIN status bytes, followed by objects. This is the layer we spend the rest of the funnel inside. Our CROB lives here.

the funnel so far

DNP3 → three layers → the application layer. Everything below this line is inside L3.

05Narrowing

Objects: groups & variations

A function code says what to do. An object says to what, and in what form. This two-part addressing is the last idea we need before the CROB clicks into place — and it's where "multiple CROBs" actually comes from.

Every piece of data DNP3 can carry is named by two numbers, written Group . Variation. They are two independent axes:

the group — what kind of thing

The data category. Group 30 is "analog input," Group 1 is "binary input," Group 12 is "binary output command." Think of it as the product line in a parts catalogue.

the variation — in what form

The encoding of that category: 16- vs 32-bit, with or without a quality flag, with or without a timestamp. One group has many variations — the same value, packaged differently.

So Group 30 Var 1 and Group 30 Var 5 are the same measurement — an analog input — in two encodings (a 32-bit integer vs a short float). Master and outstation agree per point which variation to speak. A "static" group (e.g. 30) is the current value; its paired "event" group (32) is the change report for that same value.

Explore the catalogue

Pick a group to unfold its variations — and see how the harness actually uses each. Group 12, in copper, is where the funnel is heading.

The object header — "one header, then N points"

Inside a SELECT or OPERATE, each object is introduced by a small object header: the group, the variation, a qualifier (how the points that follow are addressed), and a count. Then the point instances themselves. Below is the real header taken from our Test C SELECT capture — tap any byte to decode it:

Tap a byte above
These bytes are the object header plus the first CROB. A second point (index 1, LATCH_OFF) follows in the identical shape — that is two CROBs living under one header.

The qualifier decides how points are addressed

The qualifier byte is the quiet hero of "multiple CROBs." It picks one of three addressing styles for the points that follow the header:

0x06 · all objects

"Give me everything of this type." No indexes at all. This is what a Class-0 read uses to sweep the whole database.

0x00 / 01 · start–stop range

A contiguous block of indexes — e.g. points 0 through 9. Compact when the points are adjacent.

0x28 · count + index prefix

"Here are N objects, each tagged with its own index." Exactly what control needs — arbitrary, specific points. This is the mode that lets one header carry index 0 and index 1.

why this is the crux of the whole project

Because a CROB header uses the count + index prefix qualifier, a single Group 12 Var 1 object can front an arbitrary list of individually-indexed control points. "One header, then N points" is the mechanism behind multiple CROBs — stop 07 simply sets N = 2, and the outstation happily processes both.

06The point of the funnel

The CROB — Control Relay Output Block

Group 12, Variation 1. The single object this entire project narrows down to.

A CROB is a compact instruction to a binary output point. It bundles a handful of fields. The two that matter most to us are the point index (which output) and the control code (what to do to it).

point index

Which output point this targets. In our experiment: 0 (feeder-A) or 1 (feeder-B).

control code

LATCH_ON (raw 0x03) drives the point true; LATCH_OFF (0x04) drives it false.

count

How many times to apply it (we use 1).

on-time / off-time

Pulse timing in ms (we use 100 / 100). For LATCH they're along for the ride.

say it correctly

LATCH_ON / LATCH_OFF are control codes applied to one output point. They are not "multiple physical latches," and CROB is an application-layer object, never a function code.

08The handshake

Select-Before-Operate

Control in DNP3 is deliberately two-step, so a garbled message can't accidentally throw a breaker. The master SELECTs (arms) the exact controls, the outstation echoes them back, and only then does the master OPERATE (fires) the identical set. Press play and watch our two-CROB transaction flow:

Note what SELECT does not do: it changes no state. The outstation only records the armed request. State flips on OPERATE, and only if OPERATE matches a still-pending SELECT. That "must match a prior select" rule is the safety spine of the whole feature — and, at stop 12, the thing Test D probes.

one API call, two messages

Our master issues SelectAndOperate(command_set, …) — one library call that performs the SELECT and the OPERATE as a single task. On the wire it's still two request/response pairs; in code it's one combined task. That distinction becomes very important at stop 13.

09Widening: our work

What we actually built

The funnel's narrow point was the CROB. Now we widen back out into the implementation. The rule was minimal & additive: prove the protocol behaviour without disturbing anything already working (the Class-0 read, TCP replay and CRC-split paths were not to be touched), and without ever touching a physical device.

outstation side

A software-only control target

A new flag --control-test gives the outstation two simulated binary output points (index 0 = False, index 1 = True) living in a plain Python dictionary. It validates each incoming CROB, records SELECTs, executes matching OPERATEs, and prints its state. Without the flag, the outstation behaves exactly as before.

master side

A dedicated control action

A new action --action multi-crob-sbo builds one CommandSet with the requested CROBs and runs one Select-Before-Operate. Sub-flags --crob-test A|B|C pick the staged test; --control-test-negative runs the safety probe.

safety: only indexes 0/1 safety: only LATCH_ON / LATCH_OFF safety: OPERATE needs a matching SELECT safety: no DIRECT_OPERATE the replay/split server: untouched

Read the real pieces — switch tabs:

Pure Python, no pydnp3 — so it is trivially testable. SELECT records; OPERATE requires an exact match, flips the point, and consumes the selection so a stale arm can never be replayed.

class ControlTestState:
    # two simulated binary outputs — IN MEMORY ONLY. No GPIO, relay, or breaker.
    SUPPORTED_IX   = (0, 1)
    SUPPORTED_CODE = ('LATCH_ON', 'LATCH_OFF')

    def __init__(self):
        self.state    = {0: False, 1: True}   # simulated_output_state
        self.selected = {}                     # index -> (code, count, on, off)

    def select(self, index, code, count, on, off):
        if index not in self.SUPPORTED_IX:   return 'OUT_OF_RANGE'
        if code  not in self.SUPPORTED_CODE: return 'NOT_SUPPORTED'
        self.selected[index] = (code, count, on, off)   # record — NO state change
        return 'SUCCESS'

    def operate(self, index, code, count, on, off):
        armed = self.selected.pop(index, None)          # consume on EVERY attempt
        if index not in self.SUPPORTED_IX:        return 'OUT_OF_RANGE'
        if armed is None or armed != (code, count, on, off):
            return 'NO_SELECT'                     # nothing matches -> refuse
        prev = self.state[index]
        self.state[index] = (code == 'LATCH_ON')      # the flip: ON->True, OFF->False
        return 'SUCCESS'

    def state_block(self):
        return "Simulated CROB Output State\n" + "\n".join(
            f"  Index {i}: {v}" for i, v in sorted(self.state.items()))

A thin pydnp3 ICommandHandler turns the library's callbacks into the state machine and maps result strings to DNP3 status codes. It is swapped in only under --control-test; otherwise the outstation keeps its normal handler (controls rejected).

STATUS_MAP = {
    'SUCCESS':       opendnp3.CommandStatus.SUCCESS,
    'OUT_OF_RANGE':  opendnp3.CommandStatus.OUT_OF_RANGE,
    'NOT_SUPPORTED': opendnp3.CommandStatus.NOT_SUPPORTED,
    'NO_SELECT':     opendnp3.CommandStatus.NO_SELECT,
}

class ControlTestCommandHandler(opendnp3.ICommandHandler):
    def Select(self, command, index):
        r = self.state.select(index, code_of(command), command.count,
                              command.onTimeMS, command.offTimeMS)
        _log.info("SELECT  index=%s code=%s -> %s", index, code_of(command), r)
        return STATUS_MAP[r]

    def Operate(self, command, index, op_type):
        r = self.state.operate(index, code_of(command), command.count,
                               command.onTimeMS, command.offTimeMS)
        _log.info("%s", self.state.state_block())   # print before/after state
        return STATUS_MAP[r]

One CommandSet, N CROBs — the whole thesis. Two non-obvious details are load-bearing: keep the set alive (async task references it after this returns), and pick the callback per platform (stop 13).

def select_and_operate_command_set(self, crobs):
    # Keep the CommandSet alive on self: SelectAndOperate is ASYNC and the C++
    # task keeps using it after this returns. A local would be garbage-collected
    # mid-flight -> dangling reference -> the DNP3 thread hangs (see stop 13).
    self._cmd_set = opendnp3.CommandSet([
        opendnp3.WithIndex(
            opendnp3.ControlRelayOutputBlock(getattr(opendnp3.ControlCode, name)),
            index)
        for index, name in crobs          # e.g. [(0,'LATCH_ON'), (1,'LATCH_OFF')]
    ])
    # The result callback misbehaves in OPPOSITE ways per pybind11 build:
    #   3.12 -> a Python callback aborts;  3.8 -> the C++ one hangs.
    cb = asiodnp3.PrintingCommandCallback.Get() if PY312 else _noop
    self.master.SelectAndOperate(self._cmd_set, cb, opendnp3.TaskConfig().Default())

The crux. The command result can't be read from Python on this build, so we capture only the task-level status via OnTaskComplete, freeze the single DNP3 thread so the crashing delivery never runs, and do the file I/O + exit from the main thread.

class MultiCrobMasterApplication(opendnp3.IMasterApplication):
    def OnTaskComplete(self, info):                    # fires BEFORE the crash
        if info.type == opendnp3.MasterTaskType.USER_TASK and not self._fired:
            self._fired = True
            on_done(opendnp3.TaskCompletionToString(info.result))  # -> 'SUCCESS'

result_ready = threading.Event(); box = {}
block_forever = threading.Event()                      # never set()

def on_done(status):                                     # runs on the DNP3 thread
    box['status'] = status
    result_ready.set()
    block_forever.wait()      # never returns -> the ONE DNP3 thread is frozen -> no abort

master.select_and_operate_command_set(crobs)
result_ready.wait(timeout)                              # main thread waits for the status
write_summary(box.get('status'), ...)                # file I/O is SAFE here, off the DNP3 thread
os._exit(0)                                          # clean exit, before any teardown crash

Design choices worth naming: the state lives in a plain in-memory dict (the spec asked for exactly that), the change is purely additive (the read/replay/split code is untouched), and the safety defaults are strict — only indexes 0/1, only LATCH_ON/OFF, OPERATE requires a matching SELECT, and DIRECT_OPERATE is never used.

12Proof by staging

The four tests

We didn't jump to two CROBs. We climbed a ladder — prove one control works, prove the other index and code work, then two-in-one, then deliberately break it to see the failure mode.

The reset problem, and how we handle it. Each test needs the outstation at a known start (index 0 = False, index 1 = True). But after a test the state has moved, and DNP3 has no "reset your simulation" message. So each staged test runs against a freshly restarted --control-test outstation — a new process is the only honest reset, and it mirrors how the harness already restarts servers per phase. That's why Test B, which targets index 1, starts from a clean board rather than A's leftovers.

Test D — reading the failure precisely

D is the most informative test, because a careless implementation could get it dangerously wrong (e.g. firing the valid control anyway). We report only what OpenDNP3 actually did, split by phase:

at SELECT

The outstation accepts index 0 (recorded) and rejects index 99 as OUT_OF_RANGE. The master's per-index result shows idx 0 SELECT_SUCCESS and idx 99 SELECT_FAIL.

at OPERATE

The master issues no OPERATE at all — a SELECT failure on any one CROB aborts the OPERATE for the whole set. Index 0 therefore never fires; its final status is undefined.

So the valid control never executes and no output changes unsafely — index 0 stays at its initial False. We deliberately do not generalise this into a rule ("partial success" vs "whole-command failure"); we report the one behaviour this stack exhibited, on this run.

where "both changed" is actually proven

Note the master reports a task-level outcome, not a per-index one — the per-command result was the un-readable object from stop 13. So the authoritative evidence that both outputs changed is the outstation log above and the packet capture (stop 14), not the master's single SUCCESS. That is a strength, not a gap: the outstation is the party that actually acted.

13The hard part

The debugging journey

The protocol worked on the very first rig run. The tooling did not. Here is the honest sequence of walls — each one looked like the answer until it wasn't.

The recurring, maddening theme: every time, the DNP3 exchange on the wire was perfect — the outstation processed both CROBs and flipped its outputs correctly — yet the master process died or froze after the exchange, while trying to hand the result back to our Python code. Expand each hurdle:

The CommandSet was a local variable. SelectAndOperate is asynchronous, so the function returned and Python freed the object while the C++ task was still using it — a dangling reference that froze the DNP3 thread.
fix
Keep the CommandSet alive by stashing it on the object for the task's lifetime.
lesson
Async + a garbage collector = you must anchor anything the background task still references.
wall 6

diagnosis
Doing blocking file I/O on pydnp3's single callback thread deadlocks against its C++ internals.
lesson
You may capture on the callback thread, but you must not do work on it. Hand off, don't process.

the fix
pydnp3 runs a single DNP3 thread. In OnTaskComplete we hand the result to the main thread, then block that one thread forever. Frozen, it can never deliver the crashing result. The main thread — free and safe — writes the summary and calls os._exit(0).
result
Clean exit code 0, summary written, no abort, no hang — on both Python 3.12 and 3.8. Every test A–D passes on the rig and loopback.
the trade
The master can't read per-index status (that lived in the un-readable result). So per-index proof comes from the outstation log + the packet capture instead — which is more authoritative anyway.

15Pushing the envelope

The boundary — valid, invalid, too many

Tests A–D proved two CROBs ride in one transaction. The obvious next questions: how many fit, and what exactly happens at the edges — a point that doesn't exist, or one control too many?

First, how many. A highest-N sweep pushed a single command set to N = 1, 2, 4, … CROBs and hit a hard ceiling: Nmax = 16. At N ≥ 17 the outstation accepts the first sixteen and rejects the rest with TOO_MANY_OPS — OpenDNP3's maxControlsPerRequest default. The master then issues no OPERATE, so nothing applies. This is a count limit, not a fragmentation one — seventeen CROBs still fit comfortably in one link frame.

Then, the sharper question. A rejection can mean two very different things, and they carry two different status codes on the wire:

status 0x0C = 12   OUT_OF_RANGE

The requested output index does not exist on this outstation (its supported set is 0…K−1). Rejected per-index, at the command handler.

status 0x08 = 8   TOO_MANY_OPS

There are more controls in one request than maxControlsPerRequest allows. Rejected at the stack, for the op past the limit — whether or not that index exists.

To tell them apart we configured the outstation with only K valid points and sent an explicit, ordered plan of CROBs — some real, some not — through a new --crob-plan flag. Explore the boundary yourself: set K, pick a plan, and each op resolves exactly as the rig reported it.

the one capture that shows both

With K = 5, N = 17 a single SELECT response carries both codes at once — SUCCESS for indexes 0–4, OUT_OF_RANGE for the eleven nonexistent indexes 5–15, and TOO_MANY_OPS for the seventeenth op. Two rejection mechanisms, one packet, each resolved per-index and unambiguous. With K = 16 the count limit alone fires: the first sixteen succeed and only the seventeenth is rejected.

what this means for the padding idea

Invalid-index CROBs never execute a configured output — but they are far from invisible: every one appears as a non-success status in the SELECT response. And because a partial SELECT failure blocks the OPERATE for the whole set, an invalid "padding" CROB can't be smuggled into a real control transaction without extra response-side handling or a different cover-traffic design. This characterises the behaviour; it does not implement padding, and it is not a claim that padding works.

Where each rejection lives

The two status codes are not two flavours of one check. They are raised in two different places inside the outstation, and one of them fires before our code ever runs. Follow a SELECT carrying N CROBs left to right:

TOO_MANY_OPS is decided by OpenDNP3 itself, so the ops past the sixteenth never reach our ControlTestState at all — that is why it is a count limit and not an index check. OUT_OF_RANGE is our own per-index test in the command handler. And the batch rule is the reason a single failure anywhere in the set blocks the OPERATE for every index: a partial SELECT is abandoned whole, so no valid control is ever left armed on a half-failed request.

why the K5·N17 packet shows both

The gates sit in series, so one request can trip both. With K = 5, N = 17 the seventeenth op hits the stack gate (TOO_MANY_OPS) while indexes 5–15 reach the handler and fail there per-index (OUT_OF_RANGE), and indexes 0–4 pass both. Raise the valid set to K = 16 and the handler stops objecting — only the count gate is left, so just the seventeenth op is rejected.

The code behind the boundary

Three small pieces produce every row of the table above: the outstation's per-index check and its batch-discard rule, the master's ordered --crob-plan, and the analyzer that reads a verdict straight off the wire. Switch tabs:

OUT_OF_RANGE is one if: the supported set is 0 .. K-1, and any index outside it is refused before the selection is ever recorded. The batch rule is the second method — one failed object drops the whole SELECT, which is what stops a half-failed set from arming a real control.

def _validate(self, index, control_code):
    # OUT_OF_RANGE lives HERE, in the command handler — decided per index.
    if index not in self.supported_indexes:        # supported_indexes = range(K) = 0 .. K-1
        return 'OUT_OF_RANGE', 'index {} not in supported set 0..{}'.format(
            index, self.control_point_count - 1)
    if control_code not in self.supported_codes:
        return 'NOT_SUPPORTED', 'control code {} not supported'.format(control_code)
    return 'SUCCESS', None

def discard_selections(self, indexes):
    # Any object in a SELECT batch failed -> abandon the WHOLE batch, so a
    # partial failure never leaves a valid control armed. THIS is why one
    # OUT_OF_RANGE anywhere blocks the OPERATE for every index in the set.
    return [i for i in indexes if self.selected_commands.pop(i, None) is not None]

The plan is an ordered list of CROBs, parsed from idx:CODE,idx:CODE,…. It deliberately allows an index the outstation does not have — that nonexistent index is the whole experiment — and validity is read back from the response, never enforced here. One plan becomes one CommandSet and one SelectAndOperate.

def _build_crob_plan_from_spec(spec):
    # Parse --crob-plan "idx:CODE,idx:CODE,..." in TRANSMITTED order.
    # An index may be nonexistent on the outstation — that is the point of
    # the invalid-index tests; validity is characterised from the response.
    crobs, seen = [], set()
    for e in [e.strip() for e in spec.split(',') if e.strip()]:
        idx_s, code = (p.strip() for p in e.split(':'))
        idx, code = int(idx_s), code.upper()
        if code not in CROB_PLAN_SUPPORTED_CODES:
            raise ValueError('unsupported control code {!r}'.format(code))
        if idx in seen:
            raise ValueError('duplicate index {}'.format(idx))
        seen.add(idx); crobs.append((idx, code))
    return {'crobs': crobs, 'expected_states': {i: (c == 'LATCH_ON') for i, c in crobs}}

def _resolve_crob_plan(args):
    # Precedence: --crob-plan > --crob-count > --control-test-negative > --crob-test
    if getattr(args, 'crob_plan', None):
        return _build_crob_plan_from_spec(args.crob_plan)

16Honesty & horizon

What this does not prove — and where it goes next

Good validation is precise about its own edges. This establishes a narrow, well-characterised claim: this controlled OpenDNP3 master/outstation pair encodes and processes multiple valid CROBs in one Select-Before-Operate set — up to 16 — and rejects invalid or excess ones in known, per-index ways. Everything below is out of scope — deliberately, and with a reason for each.

The limitations, and why each holds

✕ Not physically simultaneous
why
The outstation processes the CROBs one Operate callback after another, in order. "One message" is not "one instant."
and
These are simulated points in a dictionary — nothing physical moves at all.
✕ One "success" ≠ both outputs changed
why
The master could read only the task-level status, not per-index — the per-command result was the un-readable object from stop 13.
so
Proof that both changed comes from the outstation log + PCAP, never from the master's single SUCCESS.
✕ Not vendor-universal
why
We proved it for the OpenDNP3 stack. A physical relay from vendor X may cap the number of CROBs per set, or reject multi-object controls entirely.
✕ Invalid indexes are characterised, not "safe"
why
Section 15 maps exactly how a nonexistent index is rejected (OUT_OF_RANGE, per-index) and how a partial SELECT failure blocks the whole OPERATE. Knowing the response is not licence to inject fake controls as padding.
✕ Not yet an obfuscation defence
why
We showed the protocol allows structure variation. We have not measured whether varying it actually defeats a passive fingerprinter — that is a separate experiment.
✕ Says nothing about P4 / Tofino
why
This is a software validation over the management network. In-network / dataplane feasibility is a different phase, gated until explicitly started.

Where this sits — and what's above it

The result is one rung of a taller ladder. Being honest about which rung keeps the claims defensible:

doneProtocol / API: OpenDNP3 accepts N CROBs in one Select-Before-Operate set.
doneEnvelope + boundary: Nmax = 16; nonexistent index → OUT_OF_RANGE, over-limit op → TOO_MANY_OPS — mapped per-index from the PCAP.
you are hereValidated software-only on the real rig up to N = 16, with the invalid-index and over-limit edges characterised.
nextObfuscation value — does valid multi-CROB structure variation actually lower a passive fingerprinter's accuracy?
laterReal relays — does a physical vendor device behave like OpenDNP3?
gatedIn-network / P4 dataplane realisation.

Three concrete next experiments

the fingerprint test

Feed varied-structure control traffic — N and control codes varied within the proven 1–16 envelope — to a passive classifier and measure whether the shaping actually lowers device identifiability. The metric that turns "allowed" into "useful."

the timing dimension

Structure is one axis; size and timing are the others. Record whether packing N valid CROBs shifts the response length, segmentation, or round-trip — the size/timing signature the wider obfuscation project actually targets.

the vendor question

Point the same master at a real relay. OpenDNP3 says yes — and caps at 16; a physical vendor device may cap differently or refuse multi-object controls entirely. That leap is where the research earns its keep.

the takeaway

A DNP3 outstation happily reads and acts on multiple control objects packed into one Select-Before-Operate transaction. The protocol says yes. The pcap proves it. And the tooling — eventually — agrees.
