Tofino-1 · DNP3 · in-network timing defense

Holding a packet on a switch that cannot hold packets

A protection relay answers its SCADA master in 1–5 ms, and that interval identifies the device. This is how a Tofino ASIC — a chip with no timers, no queues it can write to, and no ability to delay a frame — is made to release every response at exactly the same instant relative to its own ACK, on real hardware, inline with a live SEL‑751.

01 — the channel

What CLRT is, and why it identifies a device

A DNP3 outstation on TCP answers a poll in two separate packets. First its TCP stack acknowledges the request — a bare ACK carrying no payload. Then, once the application has actually assembled the answer, it sends the DNP3 response. The gap between those two is the Command Loop Response Time, and it is a property of the device, not of the network: it measures how long that particular firmware, on that particular processor, with that particular point map, takes to build a reply.

Formby's fingerprinting work turns this into an identification technique. You do not need to read the payload, break encryption, or send anything at all. You watch the gap. Different relays cluster in different places, and the shape of the cluster is the signature.

Which means the defense has to attack the shape, not the average. Shifting every response later by a constant would preserve the distribution perfectly and reveal exactly as much. The only thing that works is collapsing the distribution to a single value.

02 — the position

Why a tap is useless and the switch has to be in the path

The defense delays the relay's response. You can only delay a packet you are forwarding — a mirror port or a passive tap sees a copy after the original has already gone. So the Tofino has to be a bump in the wire, and the relay must have exactly one route to its master, through the switch.

That sounds obvious and is easy to get wrong. In the first attempt the relay sat on an unmanaged switch, the Tofino uplinked to that same unmanaged switch, and the master was also plugged into it. Every frame was switched locally between two ports and the Tofino saw only flooded broadcast. The counter that proved it: the port facing the relay had transmitted zero frames, ever.

The proof that it is really inline is the inverse test, not the ping. With the relay leg administratively disabled the master must lose the relay entirely. Measured: leg up 3/3 replies, leg deleted 0/3, 100 % loss, leg restored 3/3. If it still answered with the port down, some other path existed and none of the rest would mean anything.
03 — the mechanism

The pipeline, one packet at a time

Here is the difficulty. A Tofino forwards at line rate and has no notion of "later". There is no timer you can arm, no way for the control plane to reach into a queue, and no instruction that means wait. The chip's only native behaviour is: parse, match, act, leave.

04 — the obstruction

A reservoir of packets that chase their own tail

The obstruction is built from packets. The response is steered onto a low-priority queue on the dp8 loopback; a crowd of small internal frames — blocker tokens, ethertype 0x88C1 — is steered onto a high-priority queue on the same port. Tofino's traffic manager honours strict priority, so as long as any blocker is queued, the response is never selected for transmission. The blockers loop through the pipeline and re-enqueue themselves, so the crowd sustains itself with no host involvement.

Two details that were learned the hard way and are easy to get wrong:

Strict priority is a field you must actually set

The first version of this failed completely, and the cause was configuration, not architecture: only min_priority was being programmed. The field that arbitrates remaining bandwidth is max_priority, and with it unset both queues shared bandwidth fairly — so the "blocked" response drained straight out. Setting max_priority = 7 on the blocker queue is what makes the gate absolute.

One blocker is not enough — you need a crowd

A single circulating token leaves gaps. While it is in flight through the pipeline its queue is momentarily empty, strict priority finds nothing to serve there, and the held response escapes through the hole in about half a microsecond. The queue has to be occupied continuously, which means enough tokens in flight to cover a full pipeline-plus-loopback traversal. Measured on this chip: K = 1, 8, 18 and 32 all leak; K ≥ 64 holds with zero escapes.

Isolation. A blocker token must never reach a host. The parser forces any 0x88C1 frame to ROLE_BLOCK regardless of where it came from, so an injected frame cannot talk its way onto a host port. The check is that eth.type==0x88c1 stays empty in a host-side capture, and that the outstation-facing port's transmit counter stays at zero for those frames.
05 — the release

How the data plane learns what time it is

Nothing so far has said when to let go. There is no timer, and the control plane is far too slow and too jittery to be in this loop — we are targeting microsecond-scale precision on a millisecond-scale interval.

So the deadline is evaluated by the blockers themselves. When the relay's ACK passes through, the pipeline stamps reg_t_ack from the ingress timestamp and writes reg_deadline = t_ack + G. Every blocker, on every lap, compares the current time against that deadline. While it is early, it re-circulates. On the first lap where it is late, it terminates instead of re-enqueuing. The crowd drains, the high-priority queue empties, strict priority finally serves the low-priority queue, and the response leaves.

The release time is therefore decided entirely on-chip, by the packets, with no external clock or controller.

A compiler constraint that shapes the code

Writing that comparison is harder than it reads. A bit-slice inside a gateway condition is rejected outright as too complex, and slicing a 32-bit arithmetic field breaks PHV allocation entirely. So expiry is decided by a ternary match on the sign bit of (now − deadline) — the same bit the arithmetic would have tested, reached without slicing anything.

06 — the parameter

Choosing G, and the failure that leaves no trace

G is the guard interval — the constant every CLRT becomes. It is the only tuning knob, and it has an asymmetric failure mode that is worth feeling rather than reading.

You can only add delay. If a transaction's native CLRT is already larger than G, there is nothing to hold back: it passes through untouched, at its true timing, and nothing on the wire indicates that it did. Drag G below the tail of the real distribution and watch the entropy refuse to reach zero.

This is not hypothetical. Two native runs on this relay produced maxima of 22.66 ms and then 37.22 ms. Against the G = 25 ms we first ran, that second transaction would have escaped silently. The tail is the thing to characterise before choosing G — and any protected run should report its zero-hold count, because a run with escapes is not a protected run.

The ceiling is set from the other side. The held segment is one the relay sent, so if the hold outlives the relay's TCP retransmission timeout it will resend — duplicating the response and creating a fresh, very visible artifact. Measured at G = 25 ms: zero retransmissions, zero duplicate ACKs, zero reordering. The DNP3 application layer imposes nothing here at all, because the responses carry CON = 0 and the session uses unconfirmed link service, so no application timer is ever armed.

There is also a subtler cost. A device that natively answers in 2 ms but always answers in 40 ms is itself distinctive. Normalization removes the variance an attacker fingerprints, but the constant is visible. If the goal is to hide within a population, G should be chosen to look like a plausible member of it — which is where the 17 and 25 ms candidates came from originally, being the relay's own native p95 and p99 in the capture corpus.

What this does not show

It is not a byte-identity proof. The relay is live, so its measured values legitimately change between runs, and the relay leg cannot be tapped — the unmanaged switch has no span port — so the same frame cannot be compared on both sides here. Byte identity rests on the earlier replay campaign, where it held 100/100. What this run does support is weaker and still worth stating: constant response size, nothing malformed, and no TCP anomalies.

It is also not anonymity. This closes the CLRT channel. Response size, ACK mode, and the TCP stack fingerprint are untouched, and on this corpus the SEL‑751 is the only separate-ACK device — an anonymity set of one. Normalizing when a device answers does not make it look like a different device.

08 — reproducing it

Running it yourself

From ~/dnp3_live on the master host. The switch keeps running the same program throughout; nothing is reloaded between native and protected.

./status.sh                       # 4 preflight checks; refuses to lie about readiness
./run.sh native                   # 20 read-only polls, nothing held
./run.sh protected                # same polls + 64 blocker tokens (needs sudo)
./clrt.py native.pcap protected.pcap

To watch it live instead of after the fact, capture on the master leg and filter to ip.src == 192.168.10.7, then set the time column to Seconds Since Previous Displayed Packet. You are now looking at only the relay's own packets, alternating ACK and response — and the number on each response row is the CLRT. It jitters between 0.001 and 0.005 during a native run and pins to 0.025 the moment the tokens start flowing.
