## 3. Implementation findings requiring action

### A. High: the evaluated P4 still prevents recovery of a lost OPERATE

**Sources:** `defense4/timing/implementation/exact_experiment_source/defense4_rrc_bor_unified12.p4`, lines 1772–1781, 3201–3225, 3264 and 2340; `audit_current/OPERATE_RETRANSMISSION_RISK_20260916.md`.

This is **documented, not fixed**. The program retains the OPERATE application generation after release. A subsequent matching generation becomes `V_OP_DUP` and reaches `cmt_drop()`, until a new SELECT clears the marker.

If the released OPERATE is lost between switch and relay, the master retransmits the missing TCP bytes. The retained marker causes that repair packet to be discarded as well. Forwarding a packet once is not evidence that its receiver received it. TCP reliability depends on allowing retransmission of missing sequence ranges. [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html).

The campaign's successful OPERATE exchanges do not exercise this loss path. The archived response-drop diagnostic is in the other direction and does not test it either. This remains a high-confidence source-level finding, not a reproduced hardware failure.

**Paper consequence:** the current manuscript still says exchanges lose protection “but not [their] delivery,” and its limitations do not explain the known spent-OPERATE defect. The introduction continuation also says every DNP3 byte reaches the master unchanged. Byte preservation, delivery preservation and successful delivery in the recorded workload are different claims.

**Required action:** preserve the frozen evidence; state its loss-recovery limitation in the manuscript; develop any correction as a separate candidate with its own validation. Do not describe a correction document as a corrected implementation.

### B. High before implementation: the proposed repair flag conflicts with the existing encoding

**Sources:** `audit_current/OPERATE_RETRANSMISSION_RISK_20260916.md`, lines 103–115; frozen P4 parser line 1462 and generation-domain comments around 1515–1522.

The proposal says the generation already occupies only the low nibble and that the high bit can become a released flag. The current program instead assigns:

`meta.gen_in = hdr.dnp3_app.app_control`

and uses generations in **`0xC0..0xCF`**. Every one already has bit `0x80` set. Reusing that bit without changing the encoding would make a held generation look released. Simply masking to the low nibble creates a second problem: sequence zero would collide with the inactive sentinel `0x00`.

The repair idea—distinguishing held copies from post-release transport repair—is sound. Its proposed representation is incomplete and must not be implemented literally. Define an encoding with distinct inactive, held and released states for all sixteen application sequence values, and audit every reader and writer.

The proposal also claims forwarding a repair cannot disturb another transaction. That is not established: shared sequence/ACK trackers are updated before the final forwarding/drop verdict. The acceptance cases must include a delayed repair arriving during a subsequent transaction, not only one isolated SELECT/OPERATE.

### C. Medium: admission binding is improved but still incomplete

**Source:** `active_control/timing_only_profile.py`, `_admission_problem()` at 345 onward.

The earlier empty/unknown/provisional verdict bypass and different-delay example are fixed. Build, queue and port validation are also stronger. However:

- A record containing only `admitted_conditional` and matching delays, with **no context or checks**, still activates.
- A genuine evaluator result for another connection still activates. The activation profile has no connection identity against which to compare it.
- Build identity is checked only when present. Missing identity is accepted.

Both first cases produced `activated` and nine writes using only the repository's `RecordingDevice`. No actual switch was used. The remaining defect is a missing binding between admission and deployment, not a claim that this module already has a hardware adapter; it explicitly does not.

**Required action:** make the expected build and connection context mandatory at activation, validate the admission schema, and require complete supporting checks for the policy being installed. Match the quantized policy consistently. Do not use a caller-supplied verdict label as the whole authorization record.

The admission module now checks direction and timer role correctly. Its prose still calls every input an observed maximum, despite the native CLRT input needing a lower bound and an allowable timer budget needing suitable conservative headroom. Observation dates are only checked for non-emptiness, not validity or applicability after reconnection. Keep these distinct roles explicit.

### D. Medium: probe cleanup still has an uncovered installation failure path

**Source:** `active_probe/rto_probe_plan.py`, `run_steps()`, especially lines 383 and 406.

The blocked-workload defect is partly resolved: a separate worker lets the supervisor remove the rule when its watchdog expires. The offline blocked-workload check returned `watchdog expired`, verified cleanup, and explicitly reported abandonment. The worker itself continues until released; this is bounded rule supervision, not cancellation of the workload.

Two remaining counterexamples:

1. A runner performs the installation, then raises while returning its result. The install call lies outside the cleanup-protected block. The function raises plain `OSError`, supplies no execution record and attempts no cleanup. In the test double the rule remained installed.
2. `plan()` rejects NaN, but an executable plan is a mutable dictionary. Replacing its hold with NaN before `run_steps()` produced `completed`, elapsed zero and four runner calls. Execution does not revalidate its duration fields.

**Required action:** cover attempted installation and an uncertain install result with ownership-scoped cleanup and recording; validate finite hold/watchdog values at execution; bound waits by the remaining deadline. State the separate lifecycle of a workload that cannot be cancelled. These are offline corrections and require no live probe.

### E. Medium: partial activation reporting misses a successful write followed by failed readback

**Source:** `timing_only_profile.py`, `_partial()` at 429 onward.

The record now retains more failure evidence, but it derives `partial_configuration` only from successfully verified steps. A successful first write of `shape_enable=0` followed by a readback exception produced:

`partial_configuration: false`, `left_active: []`

although the test double recorded the write and changed state. A failure to verify is not evidence that no mutation occurred. Track attempted writes, completed writes and verified state separately, and treat an uncertain write result conservatively.

This module is still a plan/verification harness. Its activation sequence also assumes a suitable starting device state; it does not establish quiescence before clearing registers. Keep that limitation explicit rather than presenting it as a complete deployment path.

### Limits of the data and validation

The campaign captures have **microsecond resolution**. Integer-nanosecond arithmetic preserves their values without epoch-float error; it does not create nanosecond measurement precision. Later diagnostic PCAPs have nanosecond resolution and must remain a separate evidence set.

The canonical extractor checks CRCs, counts and acknowledgment coverage, but it still associates the next response with the pending request without checking its application sequence, and its status summary checks one CROB status. The independent audit in this review checked the omitted sequence and all control-point statuses and found no dataset problem. Add those checks to the canonical validator so future “zero problems” results cover the same properties automatically. No new capture is needed.

The 22 groups are one campaign, not independent devices or deployments. Current classifier folds appropriately leave out grouped runs, and the paper correctly labels their ranges descriptively. Keep bootstrap uncertainty scoped to the within-campaign comparison.

### The master timer evidence

The master capture independently yields repetition gaps of:

**200.822, 208.011, 408.015, 855.997, 1663.992, 3263.998, 6720.006 and 13312.000 ms.**

The revised Evaluation correctly calls the first value an observed repetition threshold, not a socket-RTO readout. The diagnostic's `RESULT.md` still has contradictory concluding sentences claiming that it supplies a measured master timer and proves the host does not use the RFC floor. Those conclusions do not follow after acknowledging the possible distinction between an early probe and RTO expiry. Preserve the measured intervals; qualify the timer inference. [RFC 6298](https://www.rfc-editor.org/rfc/rfc6298.html).

### Epsilon is useful evidence, but the meeting's physical measurement is not complete

The twelve decoded rows and restored compile/loader records are real progress. The current manuscript correctly calls the result an **internal blocker-termination interval** and no longer asserts a bound on physical epsilon in either direction.

However, the last recirculated blocker's ingress timestamp is not a queue-empty timestamp or the held packet's actual departure. Wildcard-pipe reads and untagged transaction association also remain explicitly unverified in the audit. The 200-poll comparison is one configuration and does not establish that instrumentation is non-perturbing.

Do not use 1.7 µs as a universal safe-release allowance, or attribute the campaign's residual variance to this measurement. The next measurement, if separately undertaken, must establish the physical endpoints and transaction association first. This review did not initiate it.

## 6. Paper versus design and implementation

### Corrections still needed outside the protected introduction

1. **Abstract:** “Neither release depends on how long the device took” is too broad. The read deadlines depend on the device's ACK-arrival event. Their ideal difference cancels the native ACK-to-response interval for an on-time response; neither absolute departure nor the request-to-ACK interval becomes independent of device behavior. State the cancellation, not independence of both releases.

2. **Design's event definitions:** `e_A` and `e_R` first mean actual departures, then become exact scheduled release instants in Equation 4. `D_A = e_A − t_A` similarly mixes actual hold with a configured hold that excludes release delay. The added paragraph acknowledging scheduled instants improves the prose but leaves the mathematical definitions inconsistent. Distinguish configured and realized quantities in words and equations while preserving the established notation; do not introduce unrelated new symbols.

3. **Native CLRT:** `t_R − t_A` is a switch-arrival interval, not an exact measurement of internal execution time. Differential transport/queueing and ACK behavior can contribute. The revised Background acknowledges some of this; the Design should use the same precision.

4. **Late packets:** the implementation correctly describes qid4 service rather than an instantaneous bypass. Avoid the universal claim that every late case must be observed strictly above the target: the measured gap also contains the difference of the two release/path delays.

5. **Reply queues:** `05_implementation.tex:68–81` says the treatments have separate queues so neither can delay the other. The additional control pair on dp10 holds the **OPERATE request**. Both classes' ACK/response releases use the shared scheduling machinery. Explain that distinction directly. Shared single-slot state remains the limiting assumption.

6. **Busy transactions:** forwarding a busy packet does not establish that it cannot affect the current transaction. `exp_seq_w` and `exp_ack_w` execute before the busy outcome. Limit the claim to the evaluated serialized workload unless the shared-state effects are separately established.

7. **Fail-open and delivery:** broad preservation language remains inconsistent with the known OPERATE retransmission defect. Add that defect to the limitations and narrow the general statement. A later paragraph about late response copies does not disclose the distinct OPERATE case.

8. **Admission:** Design now correctly distinguishes an advisory horizon, a 40 ms clamp and an out-of-region sweep. Implementation still says the control plane refuses the admissible-budget violations, which conflicts with that explanation and the sweep. Name the actual configuration path and check that it enforces what the prose says. The future admission module is not what produced the campaign.

9. **Three constraints:** the paper should state briefly that holding the response postpones the master's ACK back to the outstation and therefore consumes the outstation's TCP feedback budget too. That is distinct from the master's request timer and the application's response requirement. Do not silently credit the evaluated frozen path with the active module's later checks.

10. **Security scope:** the adaptive CLRT-only result is now correctly reported as chance, and combined-feature recovery as residual leakage. Keep both. The experiment supports transaction-class timing results for one relay, not device indistinguishability or complete resistance to Formby's accumulated-distribution attack.

11. **Related Work:** the sentence after Kohno and GTID claims the framework removes the timing features those methods rely on. It does not establish removal of TCP clock skew or every packet-timing signature. Describe those works' objectives respectfully, then contrast their observable with the CLRT addressed here.

12. **Future work:** “Closing the residual requires both paths to be timed from the same event” is stronger than shown. A common reference is one proposed direction, not a proved necessary condition among all possible defenses.

### Contradictory authoritative documents need repair together

`defense4/timing/NOTATION_MAPPING.md` still contains all of the following:

- A table defining `D_R = m_R − t_R`.
- A later statement that full `D_R` is not `m_R − t_R`.
- A table calling `m_R − t_R` measured, although `t_R` is not captured.
- An “exact identity” for `D_R` that omits the outstation-to-switch segment.
- Stale epsilon lower-bound and late-forwarding claims.

`DR_LIN_WRITING_GUIDE.md` and `paper/rewrite/README.md` repeat older definitions, including `CLRT = D_R`. The guide also carries conflicting instructions about whether protected text can be edited. These are direct sources of future regression, because an editor following the documented authority can undo a correct manuscript paragraph.

Use one current definition table and one current evidence-status table. Mark old meeting interpretations as superseded rather than leaving contradictory rules active. Preserve archived code field names such as `D_R_ms`; the problem is their mapping to paper quantities, not the historical field name.

## 7. Dr. Lin's writing philosophy and voice

**The structure is much closer; the prose is not yet consistently in his register.** The protected introduction remains intact. The model precedes P4 details, the parameter discussion explains why constraints matter, and Evaluation asks questions the design raises. Related Work generally credits earlier approaches and describes differences without dismissing them. Those are substantial improvements.

The main remaining stylistic problems are:

- **Too much commentary about the paper itself.** Phrases such as “the second interval needs a careful statement,” “what that does not show,” and “the probe reaches less far than we first read it” narrate the authors' review process. Replace them with the current technical statement and its evidence.
- **Repeated scope explanations.** One device, unobserved `J`, no physical actuation, and the residual ACK channel recur in several sections. Keep the premise in the threat model, the evidence in Evaluation and the consequence in Limitations. Cross-reference instead of re-explaining.
- **Long sentences carrying several jobs.** Some sentences combine the mechanism, the measurement, a caveat and an implication. Dr. Lin's introduction advances one reason at a time, supported by a concrete example. Recover that progression rather than adding more connective words.
- **Absolute summaries followed by later exceptions.** “Removes the device's variation entirely,” “every DNP3 byte reaches,” and “preserving delivery” create claims that later sections must retract. State the supported condition at the point of the claim.
- **More caveats than the reader needs in a figure caption.** Essential definitions and scope belong there; provenance history and a full statistical paragraph do not. Move methods into the surrounding text or artifact notes.

Respectful comparison does not require generic praise such as “these defenses are effective” or “the attacks ... are correspondingly strong.” Explain what each work targets, the assumption it makes and the precise reason the current setting needs a different treatment. Do not present an unaddressed feature as another contribution.

For example, an editable mechanism paragraph could read:

> The switch computes both release deadlines when the outstation's acknowledgment arrives. For a response that arrives before its deadline, the scheduled interval equals the configured CLRT_new. The native ACK-to-response interval therefore does not appear in that scheduled gap. Actual departures also depend on blocker termination and queue service, which leave a residual in the measured interval.

An editable result paragraph could read:

> On the evaluated relay, 99.86% of READ measurements fall within 0.10 ms of the configured 4 ms interval. The CLRT-only classifier remains at chance after retraining. When it also uses the request-to-acknowledgment interval, balanced accuracy rises to 0.651. The result therefore supports suppression of the targeted feature while showing residual class information in the second interval.

These are examples of argument structure, not replacements for Dr. Lin's protected wording. Any concern with his supplied introduction should be recorded for author review, not silently rewritten. Only the three identified paragraphs have a verified verbatim boundary; do not infer authorship of additional passages from the automated gate.
